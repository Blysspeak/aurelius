# Модель данных: наряд и смена

Схема базы не меняется. Задача уже хранится узлом графа с произвольным JSON в поле `data`, поэтому наряд, вердикт и следы попыток добавляются ключами. Старые задачи, у которых этих ключей нет, покрываются `COALESCE` в каждом запросе — отдельного заполнения не требуется.

Одна деталь, стоившая бы дня отладки: **`node_type` хранится с кавычками** — литерал `"task"`, а не `task`. Запрос с `node_type = 'task'` вернёт ноль строк и будет выглядеть в точности как «очередь пуста».

## Задача с нарядом

Добавляемые ключи в `data` узла задачи:

| Ключ | Тип | Смысл | Отсутствует, когда |
|---|---|---|---|
| `lease.owner` | строка | Кто держит наряд: `smena@<host>/<pid>` | наряд свободен |
| `lease.until` | ISO-время | До какого момента аренда действительна | наряд свободен |
| `lease.run` | строка | Номер прогона, выдавшего наряд | наряд свободен |
| `attempts` | целое | Сколько раз задача бралась в работу | задача ни разу не бралась (читается как 0) |
| `cooldown_until` | ISO-время | Раньше этого момента задача в пул не попадает | остывания нет |
| `fitness.verdict` | `machine` \| `human` \| `split` | Вердикт исполнимости | задача не размечена |
| `fitness.why` | строка | Какой критерий признан проверяемым действием, а при отказе — почему ни один не признан | задача не размечена |
| `fitness.of_hash` | строка | Хеш содержания задачи на момент разметки | задача не размечена |
| `done_by` | строка | `smena` для автоматически закрытых | закрыто человеком |
| `run_branch` | строка | Линия работы, отведённая под этот наряд | наряд не брался |

### Правила

- **Вердикт протухает вместе с текстом.** `fitness.of_hash` сверяется с текущим хешем содержания задачи. Не совпал — вердикт недействителен, задача из пула выпадает до повторной разметки (FR-004).
- **`fitness.why` обязателен.** Разметка автоматическая и человеком не утверждается, поэтому обоснование — единственное, по чему её ошибку можно заметить утром (FR-003a). Вердикт без обоснования считается отсутствующим.
- **`attempts` увеличивается в момент взятия, а не в момент провала.** Иначе агент, умерший до отчёта, не оставит следа и будет браться вечно.
- **Аренда вдвое длиннее стены.** Стена по времени на наряд 25 минут, `lease.until` — 60 минут от взятия. Продлевает смена, а не исполнитель: у смены есть handle процесса, у модели — только собственное мнение о том, что она жива (FR-009).
- **`run_branch` — это и есть механизм отмены.** Отменить результат одного наряда значит отбросить его линию работы, не трогая остальные (FR-028, SC-009).

## Состояния задачи и переходы

```text
                    разметка (fitness)
                          │
   ┌──────────┐  machine  ▼
   │ backlog  │───────────────► машинный пул
   └──────────┘                      │
        ▲                            │ claim: attempts+1, lease выдана
        │                            ▼
        │                       ┌──────────┐
        │  аренда истекла       │  active  │
        ├───────────────────────┤          │
        │  release: не сошлось  └──────────┘
        │  (attempts уже увеличен)   │  │
        │                            │  │ release --verdict done
        │                            │  │ (улика свежее взятия +
        │                            │  │  проверка по каждому критерию)
        │                            │  ▼
        │                            │ ┌──────────┐
        │                            │ │   done   │ done_by=smena
        │                            │ └──────────┘
        │                            │
        │  attempts достигли трёх    │ give-up --why
        │  ──────────────────────────┼──────────┐
        │                            ▼          ▼
        │                       ┌─────────────────┐
        └───────────────────────┤     blocked     │  в пул не возвращается
                                └─────────────────┘
```

Переход в `done` — единственный, который исполнитель **не может** совершить сам (FR-012). Он заявляет результат, решение принимает смена по трём условиям сразу: код возврата дочернего процесса ноль, есть успешная проверка позже момента взятия наряда, и по каждому критерию приёмки есть запись о проверке (FR-013).

Разница между `blocked` по трём попыткам и `blocked` по `give-up` — в источнике: первое означает, что задача не даётся, второе — что исполнитель распознал упор в человека. Оба выводят задачу из пула, оба несут причину.

## Вердикт исполнимости

Выносится отдельным процессом, у которого нет права записи никуда, кроме `fitness` (FR-003). Две ступени:

1. **Детерминированные гейты, без модели.** Ни одного критерия приёмки, похожего на запускаемую команду → не `machine`. Маркеры ожидания человека в тексте («дождаться», «ответ мерчанта», «согласие клиента», «созвониться», «отправить») → `human`.
2. **Дешёвый классификатор** на модели младшего класса, строгий JSON на выходе.

Задача, результат которой не проверяется отдельным действием («изучить», «разобраться», «описать»), получает `human` независимо от того, насколько выполнимой она выглядит (FR-002a). Отчёт исполнителя о проделанной работе уликой не считается: его он напишет всегда.

Вердикт `split` в пул не пускает и автоматически не расщепляется — задача целиком откладывается человеку (FR-005a).

## Сводка прогона

Кладётся файлом и записью в хранилище знаний. Наружу не уходит ничем, включая уведомление о самом факте завершения (FR-023, FR-026).

| Поле | Смысл |
|---|---|
| `run` | Номер прогона — та же строка, что в `lease.run` |
| `started_at` / `finished_at` | Границы прогона |
| `stop_reason` | Что остановило: очередь исчерпана, потолок задач, потолок времени, три подряд неудачи, сигнал извне |
| `closed[]` | Закрытые задачи: идентификатор, чем проверено, ветка |
| `blocked[]` | Заблокированные: идентификатор, причина, число попыток |
| `skipped[]` | Взятые, но не доведённые: идентификатор, что помешало |

Требование к форме одно, и оно из SC-010: по сводке должно быть видно, чем именно проверено каждое закрытие, — так, чтобы проверка одного закрытия занимала меньше минуты и не требовала открывать историю работы.
