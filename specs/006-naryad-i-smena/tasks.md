# Tasks: Наряд и смена — автономное исполнение очереди задач

**Input**: документы из `specs/006-naryad-i-smena/`
**Prerequisites**: [plan.md](plan.md), [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md), [contracts/au-task-cli.md](contracts/au-task-cli.md)

**Тесты**: включены. Не по умолчанию скилла, а по требованию конституции проекта: принцип V («Verify Before Done») требует автоматической проверки на каждое исправление, а раздел Quality Gates — прогона против настоящей базы для всего, что трогает хранилище. Наряд трогает хранилище.

**Организация**: задачи сгруппированы по историям спеки, чтобы каждую можно было закрыть и проверить отдельно.

## Format: `[ID] [P?] [Story] Описание`

- **[P]**: можно делать параллельно (разные файлы, нет незакрытых зависимостей)
- **[Story]**: к какой истории относится (US1…US4)
- В каждой задаче — точный путь к файлу

## Dependencies & Execution Order

### Зависимости фаз

- **Phase 1 (Setup)** — без зависимостей.
- **Phase 2 (наряд)** — после Setup. Блокирует US2, US3, US4. **US1 не блокирует.**
- **Phase 3 (US1, волна 0)** — можно вести параллельно фазе 2. **Блокирует фазы 4–7 своим результатом**: меньше пяти машинных задач — дальше не идём.
- **Phase 4 (US2)** — после фаз 2 и 3.
- **Phase 5 (US3)** — после фазы 4. Код пишется, но **ночной запуск закрыт до фазы 6**.
- **Phase 6 (US4)** — после фазы 2; обязана быть закрыта до первого прогона без присмотра.
- **Phase 7 (US1 продолжение)** — после фазы 3, независима от остальных.
- **Phase 8 (Polish)** — в конце.

### Почему US4 стоит шестой, будучи P1

Приоритет P1 у неё не по порядку сборки, а по допуску: код цикла можно писать раньше, запускать цикл на ночь — нельзя. Задачи T035–T045 пишутся и проверяются под присмотром человека, T050 и T051 открывают дверь в автономность. Порядок задач и порядок допуска — разные вещи, и здесь они расходятся намеренно.

### Внутри историй

- Тесты наряда пишутся вместе с ним, а не после: они и есть то, чем закрывается волна.
- Модель данных до сервисов, сервисы до подкоманд, подкоманды до драйвера.
- Проверка end-to-end закрывает историю. Без неё история не считается сделанной, даже если весь код написан.

## Implementation Strategy

### MVP — это фаза 3, а не фаза 5

Обычно MVP означает первую пользу. Здесь первая история даёт нечто более ценное — **ответ, стоит ли делать остальное**. Один прогон разметки по настоящей очереди стоит минут и отвечает числом на вопрос, ради которого затевалась вся конструкция.

1. Phase 1 (Setup)
2. Phase 3 (US1) — параллельно с Phase 2
3. **Остановиться и посмотреть на число.** Меньше пяти машинных задач — дальше не идти: следующий шаг тогда не в коде, а в привычке писать задачу вместе с проверочной командой

### Дальше, если число позволило

4. Phase 2 (наряд) → доверие к выдаче задач
5. Phase 4 (US2) → доверие к закрытию
6. Phase 6 (US4) → допуск к автономности
7. Phase 5 (US3) → первая ночь
8. Phase 7 → точность разметки по факту первой ночи
9. Phase 8 → гейты и quickstart
