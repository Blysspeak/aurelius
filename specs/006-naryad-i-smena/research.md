# «НАРЯД И СМЕНА» — автономное исполнение очереди задач

Механизм, при котором агент получает задачи сам, а не по просьбе человека: владелец говорит «бери и делай, я спать», и цикл идёт до тех пор, пока исполнимых нарядов не останется. Название отраслевое — lease-based task dispatcher с drain-циклом; внутри Aurelius он зовётся **нарядом** (аренда задачи: наряд *выдают*, у него срок, его закрывают) и **сменой** (прогон до опустошения очереди).

Ключевое: «реального времени» здесь нет и не нужно. Нужен **push вместо pull** — обратный узор к нынешнему, где задача лежит, пока её не дёрнут.

---

## Спор с постановкой (первым, потому что от него зависит объём работ)

Очередь сегодня состоит из намерений, а не из нарядов. Из десяти верхних задач все помечены `critical` (то есть приоритет как сигнал мёртв), и почти все требуют человека: «написать претензию провайдеру», «дождаться ответа мерчанта», «решить с Тео вопрос согласия клиента». Агент их не закроет физически — не потому, что слаб, а потому, что другой конец задачи находится в чужой голове.

Смена, запущенная на такую очередь, кончится одним из двух: либо остановится через минуту («брать нечего»), либо начнёт врать — произведёт ложные `done` на задачах, которые не могла закрыть.

Отсюда **мера успеха**: не аптайм и не число взятых нарядов, а **число нарядов, закрытых с зелёной уликой**. Смена, закрывшая три наряда из ста и вышедшая в 03:10, — это успех.

И отсюда же жёсткое правило, держащее всю конструкцию: **задача не попадает в машинный пул, пока у неё нет хотя бы одного критерия приёмки, который является запускаемой командой.** Это переводит «исполнимость» из суждения модели в синтаксическую проверку, и на том же основании потом стоит вердикт `done`.

## Измеренная обстановка

Всё ниже проверено командой, а не выведено рассуждением. Каждый пункт менял решение.

| Факт | Чем измерен | Что из него следует |
|---|---|---|
| `node_type` хранится **с кавычками**: литерал `"task"` | `sqlite3` по копии базы | SQL с `node_type='task'` вернёт ноль строк и будет выглядеть как «очередь пуста» |
| Задача — узел графа с произвольным JSON в `data`; полей lease/attempts нет | чтение `handlers/task.rs` | наряд добавляется ключами JSON, **без миграции схемы** |
| Хуки срабатывают в headless `claude -p` полностью, включая Stop | прогон в чистом git-репо, журнал `.ulika/journal.jsonl` | гейт улик работает внутри звена; дублировать в драйвере не нужно |
| Бутстрап тривиального звена — **45509 токенов** (`cacheRead` 24313, `cacheCreation` 21186) | хук `ctx` того же прогона | мусорный наряд стоит не «мало», а полный бутстрап; отсев до запуска обязателен |
| Кап гейта улик: `blocksSincePass >= 2` отпускает ход | `hooks/lib/stop.mjs:71` | вечный толкатель на `exit 2` упрётся в чужой предохранитель |
| Боевой замер капа: 32 эпизода из 79 кончились отпуском, у **всех** ровно два блока | комментарий `stop-gate.mjs:76-81` | кап не теоретический, срабатывает регулярно |
| `catch {}` → `exit 0` в хвосте `stop-gate.mjs` | чтение файла | любой сбой хука **тихо** отпускает ход |
| На Stop висят шесть хуков, тяжелейший — `codebase-graph-reindex`, таймаут 150 с | `settings.json` | цепочка прогоняется на каждом звене: сто нарядов = сто переиндексаций |

## Обзор конвейера

```
   очередь задач (узлы графа, aurelius)
              │
   ┌─── 0. ОТСЕВ ИСПОЛНИМОСТИ ───┐      отдельный процесс,
   │   пишет только вердикт      │      права записи — только в fitness
   └──────────┬──────────────────┘
              │  machine
              ▼
   ┌─── 1. НАРЯД (claim) ────────┐      один UPDATE ... RETURNING
   │  аренда, срок, попытки      │      атомарен сам по себе
   └──────────┬──────────────────┘
              ▼
   ┌─── 2. СМЕНА (drain loop) ───┐      внешний процесс, вне Claude Code
   │  claude -p на наряд          │      потолки, стоп-кран, продление аренды
   └──────────┬──────────────────┘
              ▼
   ┌─── 3. ПРИЁМКА ──────────────┐      done ставит НЕ исполнитель
   │  улика + критерии + судья    │
   └──────────┬──────────────────┘
              ▼
        done / blocked / назад в очередь
```

Смена владеет жизненным циклом снаружи; гейт улик держит качество внутри звена. Это и есть разделение: **снаружи толкает драйвер, внутри судит ulika.**

## Компонент 1. Наряд

Аренда задачи. Добавляемые ключи в `data` — схема не трогается, старые задачи покрываются через `COALESCE`:

```json
"lease":      { "owner": "smena@host/12345", "until": "<ISO>", "run": "<runid>" },
"attempts":   0,
"cooldown_until": "<ISO>",
"fitness":    { "verdict": "machine|human|split", "why": "...", "of_hash": "<content_hash>" },
"done_by":    "smena"
```

Взятие — **одно** предложение SQL, атомарное само по себе. База в WAL, `busy_timeout` выставлен, SQLite ≥ 3.45 (RETURNING нужен с 3.35):

```sql
UPDATE nodes SET
  data = json_set(json_set(json_set(data,
           '$.status','active'),
           '$.lease', json_object('owner',?1,'until',?2,'run',?3)),
           '$.attempts', COALESCE(json_extract(data,'$.attempts'),0)+1),
  updated_at = ?4, updated_by = ?1
WHERE id = (
  SELECT id FROM nodes
   WHERE node_type = '"task"' AND deleted_at IS NULL      -- кавычки обязательны
     AND json_extract(data,'$.fitness.verdict') = 'machine'
     AND COALESCE(json_extract(data,'$.attempts'),0) < 3
     AND COALESCE(json_extract(data,'$.cooldown_until'),'') < ?4
     AND ( json_extract(data,'$.status') = 'backlog'
        OR ( json_extract(data,'$.status') = 'active'     -- брошенный наряд
             AND COALESCE(json_extract(data,'$.lease.until'),'') < ?4 ) )
   ORDER BY CASE json_extract(data,'$.priority')
              WHEN 'critical' THEN 0 WHEN 'high' THEN 1
              WHEN 'medium' THEN 2 ELSE 3 END,
            COALESCE(json_extract(data,'$.attempts'),0),
            created_at
   LIMIT 1)
RETURNING id, label, note, data;
```

Что чем закрыто:

- **Двойное взятие.** Подзапрос и UPDATE в одном предложении; второй писатель либо ждёт по `busy_timeout`, либо видит уже занятый наряд с живой арендой.
- **Упавший агент.** Просроченная `lease.until` возвращает наряд в пул. Срок аренды — вдвое больше стены по времени (60 мин при 25-минутной стене). **Продлевает аренду смена, а не агент**: у смены есть handle процесса, у модели — только собственное мнение о том, что она жива.
- **Вечное кручение одной задачи.** `attempts < 3` в условии плюс `cooldown_until = now + backoff`. После третьего провала — `blocked` с причиной; наряд выходит из пула до человека.

Реализация — подкоманды `au task claim | renew | release` в существующем CLI. **Отвергнуто: драйвер сам открывает SQLite.** Причина: в `db.rs` выставляются свои прагмы (`synchronous=FULL`, WAL, `foreign_keys=ON`), второй писатель с другими прагмами — это дублирование словаря статусов в JS и потеря контракта кодов возврата.

**`claim` обязан различать три исхода кодом возврата:** наряд выдан, нарядов нет, база занята. Иначе `SQLITE_BUSY` от ручной сессии владельца будет прочитан как «очередь пуста», и смена выйдет в час ночи, отчитавшись об успехе.

## Компонент 2. Смена

Внешний процесс, живущий вне Claude Code. Цикл: взять наряд → собрать промпт → `claude -p` отдельным процессом → дождаться выхода → приёмка → следующий.

**Один наряд — одна сессия.** Знание между звеньями передаётся не контекстом, а базой: `work_logs` на выходе, досье прошлых попыток на входе. Этот канал уже построен и проверен, строить нечего.

Отвергнуто:
- **Одна сессия на сто задач.** Компакция гарантирована, деградация с ~40% окна, и задача №70 решается в контексте, забитом мусором задач №1-69, из которых релевантны ноль.
- **Цепочка `--resume` между задачами.** Та же длинная сессия, только со швами: resume восстанавливает уже деградировавший контекст целиком. Внутри одной задачи `--resume` допустим — продолжить после блока замком, не более двух раз.
- **Пачка задач на сессию ради экономии бутстрапа.** Экономит секунды старта, возвращает отравленный контекст и ломает атомарность учёта: упал на третьей — что с первыми двумя?

**Стена по времени** на наряд (стартово 25 минут) ставится драйвером. Модель себя ограничивать не умеет; ограничивает тот, у кого есть handle процесса.

## Компонент 3. Отсев исполнимости

Отдельный дешёвый процесс **без права записи куда-либо, кроме вердикта**. Это не педантизм: агент, уже заплативший 45 тысяч токенов за бутстрап, не останавливается перед невыполнимым, а **подменяет действие** — «написать претензию провайдеру» превращается в файл `pretenziya.md` и в `done`.

Две ступени:

1. **Детерминированные гейты, без модели.** Нет ни одного критерия приёмки, похожего на запускаемую команду → не `machine`. Маркеры ожидания человека в тексте («дождаться», «ответ мерчанта», «согласие клиента», «созвониться», «отправить претензию») → `human`.
2. **Дешёвый классификатор** на модели младшего класса, строгий JSON на выходе.

Вердикт `split` — самый ценный: отсев создаёт дочерний наряд с исполнимым критерием, родителя оставляет человеку. Это и есть честный ответ на «сформирую сто задач»: сто пунктов владельца — это сто намерений, из которых отсев отжимает какое-то число настоящих нарядов.

Протухание: `fitness.of_hash` сверяется с `content_hash` узла; текст задачи поменяли — вердикт недействителен.

## Компонент 4. Приёмка

**Исполнитель не имеет права ставить `done`.** Под bypass permissions, без человека до утра, самый дешёвый путь к «задача закрыта» — объявить её закрытой; любой автономный цикл, где исполнитель ставит себе оценку, сходится ровно к этому.

Три ступени, и модель — не решающая:

1. **Заявка.** Агент заканчивает вызовом `au task release --verdict done --evidence "<команда>"`. Заявка пишет намерение и ничего не меняет.
2. **Улика.** Если наряд трогал код, ulika физически не выпустит ход без зелёной улики свежее последней правки. Замок уже стоит и достаётся бесплатно.
3. **Судья на стороне смены.** `done` принимается, только если: код возврата дочернего процесса ноль; в `act_trace` есть запись с `exit_code = 0` позже момента взятия наряда; у каждого критерия приёмки есть строка проверки в `work_logs`. Не сошлось — назад в очередь, `attempts` уже увеличен.

**«Сделал» и «сдался» — разные вердикты.** `done` → закрыто, метка `done_by='smena'` (ночь с ложными закрытиями откатывается одним запросом). `give-up --why` → `blocked`, наряд не возвращается в пул: сдача есть информация человеку, а не повод для ретрая.

**Останов смены** считает драйвер запросом к базе, а не по реплике агента: «нарядов нет» три раза подряд с интервалом в минуту → выход и сводка. Реплика «я всё сделал» неотличима от ложного `done`; ноль строк в выборке — отличим. Blocked и человеческие задачи в условие останова не входят: смена о них отчитывается, а не ждёт их.

## Компонент 5. Предохранители

Обязательны с первого дня, не «потом».

**Разрушительные действия.** Bypass permissions + сутки без надзора + модель, решающая, что запускать, — конструкция, которая рано или поздно выполнит `git reset --hard` или деплой. PreToolUse-хук с чёрным списком (механизм в окружении уже обкатан на `spike-deny.mjs`), работа только в отдельном worktree на ветке, main не трогается, контрольная метка перед каждым нарядом.

**Исходящие действия людям — запрещены полностью.** Это главный риск именно этой очереди, потому что она вся состоит из «написать мерчанту». Ложный `done` откатывается одним запросом; претензия, ушедшая провайдеру в три часа ночи, — нет. Запрет и в промпте, и deny-хуком на соответствующие инструменты.

**Ночью не пушить в remote, не мержить, не деплоить.** Мержит утром человек. Да, это противоречит «он погнал и всё сделал» — и должно противоречить: непроверенный мерж в main это не автономия, а выкатка без ревью.

**Бесконечный цикл.** Бюджеты прогона (нарядов, часов, процессов); инвариант прогресса — три подряд не-`done` останавливают **всю смену**, потому что сломанное окружение (грязный git, нет сети, кончился диск) валит все задачи одинаково и перебирать по ним очередь бессмысленно; один экземпляр смены через lock-файл с pid.

**Лимит подписки.** Стена по времени на наряд; модель по классу работы (отсев на дешёвой, исполнение на рабочей); чтение расхода из финального JSON дочернего процесса и остановка по потолку; экспоненциальный бэкофф на 429 и прекращение прогона после трёх упоров, а не долбёжка.

**Стоимость Stop-цепочки.** Шесть хуков на каждом завершении хода, один с таймаутом 150 с. Смена выставляет маркер прогона, тяжёлые хуки при нём пропускают работу, переиндексация делается один раз в конце.

## Волны сборки

Каждая волна закрывается своей проверкой end-to-end. Волна без зелёной проверки не считается сделанной.

**Волна 0 — правда об очереди.** Только детерминированные гейты отсева, режим сухого прогона, печать вердикта по каждой открытой задаче. Ни строки исполнителя.
*Проверка:* прогон по текущей очереди, на выходе одно число — сколько задач `machine`. **Если меньше пяти — волны 2-5 не начинать:** гонять некого, и следующий шаг не толкатель, а привычка формулировать задачу вместе с проверочной командой.

**Волна 1 — наряд как понятие.** `au task claim | renew | release`, ключи JSON.
*Проверка:* два процесса гоняют взятие по 200 итераций на тестовой базе — число уникально выданных идентификаторов равно числу выдач, ни одного двойного взятия; процесс, убитый посередине, — наряд возвращается в пул после истечения аренды и не раньше.

**Волна 2 — один наряд от начала до конца, руками.** Цикла ещё нет.
*Проверка:* реальный машинный наряд проходит взятие → `claude -p` → зелёная улика → закрытие; и подставная задача-обманка, чей критерий команда не проходит, **не** получает `done`, а возвращается в очередь с `attempts=1`.

**Волна 3 — смена и бюджеты.** Цикл, потолки, три-подряд-провала, lock-файл, маркер для тяжёлых хуков.
*Проверка:* прогон на пяти подготовленных нарядах, из них один заведомо падающий. Ожидаемый исход: четыре `done`, один `blocked` после трёх попыток, смена вышла сама, сводка в базе.

**Волна 4 — предохранители под bypass.**
*Проверка:* красная команда внутри тестового наряда отбита хуком, наряд не закрыт; после ночного прогона `git log main` до и после совпадает.

**Волна 5 — модельный отсев и расщепление намерений.**
*Проверка:* двадцать реальных задач владельца → вердикты → ручная сверка всех двадцати. Ошибка «человеческую пометил машинной» — критическая, именно она даёт ложные закрытия; обратная — терпимая.

---

## Что остаётся неизвестным

- **Сколько машинных задач в очереди на самом деле.** Оценка по десяти верхним — «около нуля», но это глазомер, а не замер. Волна 0 отвечает числом.
- **Цена бутстрапа в рабочем репозитории.** Измерены 45509 токенов в пустой папке, без CLAUDE.md проекта, памяти и MCP-контекста. В боевом репозитории будет заметно больше, и это число определяет, окупается ли схема на нарядах мелкого размера.
- **Поведение шести хуков Stop под нагрузкой смены.** Замер длительности цепочки с маркером и без делается в волне 3.

---

## Отвергнутые варианты

**Блокирующий Stop-хук как двигатель очереди.** Проиграл по четырём независимым причинам, каждой достаточно:

1. Кап `blocksSincePass >= 2` отпускает ход после двух блоков. Снимать его нельзя: он стоит там, чтобы сессия не заперлась навсегда.
2. `catch {}` → `exit 0` в хвосте хука: любой сбой **тихо** отпускает ход. Толкатель на `exit 2` умер бы от первого исключения, и выглядело бы это как штатное завершение.
3. Слот Stop уже несёт шесть хуков, и `exit 2` — общий канал для всех. Толкатель и гейт улик стали бы неразличимы для модели: два разных требования одним механизмом.
4. Нет рубильника. Внешний процесс убивается по pid; Stop-цикл гасится только правкой конфигурации из-под самого агента.

**Опрос по требованию (то, что есть сейчас).** Проигрывает по постановке: задача лежит, пока её не дёрнут, и цена этого — внимание человека на каждой итерации.

**Бесконечная смена, спящая до утра.** Токенов не жжёт, но держит взведённым агента с bypass permissions на часы без работы. Перезапуск по расписанию дешевле и безопаснее.
