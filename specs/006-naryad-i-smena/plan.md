# Implementation Plan: Наряд и смена — автономное исполнение очереди задач

**Branch**: `006-naryad-i-smena` | **Date**: 2026-08-28 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/006-naryad-i-smena/spec.md`

## Summary

Механизм, который сам выдаёт агенту задачи и гоняет их до опустошения очереди. Состоит из двух половин, и разделение между ними — главное решение всей затеи.

**Наряд** — аренда задачи. Живёт внутри Rust-CLI `au`: подкоманды `claim`, `renew`, `release`, `give-up`, `fitness`. Взятие наряда — одно предложение `UPDATE ... RETURNING`, атомарное само по себе; аренда со сроком возвращает в пул задачу, чей исполнитель умер. Схема базы не меняется: задача уже узел графа с произвольным JSON в `data`, наряд добавляется ключами.

**Смена** — внешний процесс на Node, запускающий `claude -p` по одному на наряд. Он владеет потолками, стеной по времени, продлением аренды и остановкой. Базу он не открывает никогда — только через `au`.

Работа делится на шесть волн, и **волна 0 блокирующая**: она отвечает числом на вопрос, сколько задач в очереди вообще исполнимо машиной. Меньше пяти — остальные волны не начинаются, потому что гонять нечего.

## Technical Context

**Language/Version**: Rust (workspace `crates/`, издание и тулчейн проекта) для наряда; Node.js ≥ 20, ESM (`.mjs`) для смены
**Primary Dependencies**: наряд — `rusqlite` (SQLite ≥ 3.35, нужен `RETURNING`), `clap`, `serde_json`, уже присутствующие в workspace; смена — только стандартная библиотека Node (`node:child_process`, `node:fs`), новых зависимостей нет
**Storage**: тот же единственный файл `aurelius.db` (WAL), путь резолвится существующим `home.rs`. Миграция схемы **не требуется**
**Testing**: `cargo test --workspace` для наряда; сценарные прогоны на тестовой копии базы для смены — каждая волна закрывается своей проверкой end-to-end
**Target Platform**: Windows 11, основная машина владельца; кода, зависящего от платформы, не добавляется
**Project Type**: CLI-подкоманды плюс внешний оркестратор процессов
**Performance Goals**: не является узким местом. Единственное требование ко времени — взятие наряда укладывается в `busy_timeout` при параллельной ручной сессии владельца
**Constraints**: ровно одна смена одновременно (lock-файл с pid); стена 25 минут на наряд; срок аренды 60 минут — вдвое больше стены; потолки прогона по умолчанию 20 нарядов и 8 часов
**Scale/Scope**: очередь порядка сотни задач, из которых машинных ожидается единицы — это и проверяет волна 0

## Constitution Check

*GATE: пройден до Phase 0, перепроверен после Phase 1.*

| Принцип | Оценка | Чем обеспечен |
|---|---|---|
| **I. Data Durability First** | Проходит, и усиливает | Наряд не удаляет и не перезаписывает поля — только добавляет ключи через `json_set`. FR-010 прямо запрещает трактовать недоступность хранилища как «задач нет»: `claim` обязан различать три исхода кодом возврата. Это тот же класс ошибки, что описан в обосновании принципа («не прочитал» принято за «пусто»), только на новом коде |
| **II. One Local File, Many Processes** | Проходит, ключевой | Взятие наряда — одно предложение SQL, а не «прочитать, подумать, записать». Смена **не открывает базу**: в `db.rs` выставлены свои прагмы (`synchronous=FULL`, WAL, `foreign_keys=ON`), и второй писатель с другими прагмами нарушил бы требование единственного определения. Путь к базе резолвится существующим общим кодом |
| **III. Rust Clean Code** | Проходит | Новые подкоманды подчиняются тем же правилам: без `unwrap`/`expect` на рабочих путях, ошибки типизированы, классификация занятости базы — по коду ошибки SQLite, а не по тексту сообщения (это прямо запрещено принципом и одновременно требуется FR-010) |
| **IV. Surgical Simplicity** | Проходит | Миграции нет, таблиц нет, новых крейтов нет. Наряд — ключи в существующем JSON, покрытые `COALESCE` для старых задач |
| **V. Verify Before Done** | Проходит, и является предметом фичи | Вся приёмка (FR-012, FR-013) — это тот же принцип, вынесенный в механизм: исполнитель не ставит себе оценку, `done` требует улики свежее взятия наряда |
| **VI. MCP Surface Stability** | Проходит, не затрагивается | MCP-инструменты **не добавляются и не меняются**. Смена ходит через CLI. Поверхность, которую видят чужие агенты, остаётся прежней |

Нарушений, требующих оправдания, нет. Одно отклонение от привычной раскладки записано в Complexity Tracking.

**Structure Decision**: наряд живёт в существующем Rust-CLI, смена — отдельным каталогом `smena/` на Node.

Почему так, а не одним бинарём: цикл смены будет меняться каждую ночь первые недели — потолки, формулировка промпта, условия останова. На Rust каждое такое изменение означает пересборку и прохождение всех релизных гейтов хранилища, хотя к хранилищу оно отношения не имеет. Node-драйвер при этом физически не способен испортить базу, потому что не открывает её.

Почему наряд всё-таки на Rust, а не в том же драйвере: он трогает базу, а база — это то, ради чего написана вся конституция проекта. Второй писатель со своими прагмами — ровно тот сценарий, который уже однажды разрушил файл.

- длительность Stop-цепочки из шести хуков под нагрузкой смены — отвечает волна 3.

## Волны сборки

Порядок и проверки — из research.md, здесь сведены с требованиями спеки.

| Волна | Что делается | Чем закрывается | Требования |
|---|---|---|---|
| **0** | Детерминированные гейты отсева, сухой прогон, печать вердикта по каждой открытой задаче | Число: сколько задач `machine`. **Меньше пяти — дальше не идём** | FR-001, FR-002, FR-002a, FR-003a, SC-001 |
| **1** | `au task claim / renew / release`, ключи наряда в JSON | Два процесса гоняют взятие по 200 итераций: ни одного двойного взятия. Убитый процесс — наряд возвращается после истечения аренды и не раньше | FR-006, FR-007, FR-010, FR-011, SC-005, SC-006 |
| **2** | Один наряд от начала до конца руками, цикла ещё нет | Настоящий наряд закрывается с зелёной уликой; задача-обманка `done` не получает и возвращается с `attempts=1` | FR-012, FR-013, FR-014, SC-002 |
| **3** | Смена: цикл, потолки, три-подряд-провала, lock-файл, маркер для тяжёлых хуков | Прогон на пяти нарядах, один заведомо падающий: четыре закрыты, один заблокирован, смена вышла сама, сводка на месте | FR-017…FR-024, SC-007, SC-008, SC-010 |
| **4** | Предохранители под bypass permissions | Красная команда внутри тестового наряда отбита, наряд не закрыт; `git log` основной линии до и после ночи совпадает | FR-025…FR-028, SC-003, SC-004, SC-009 |
| **5** | Модельный отсев и расщепление намерений | Двадцать реальных задач владельца размечены, все двадцать сверены вручную | FR-005, FR-005a, SC-011 |

Волна 0 блокирует все остальные. Это не осторожность, а дешёвая проверка гипотезы: вся конструкция осмысленна ровно настолько, насколько очередь состоит из задач с проверяемым критерием, а сегодня она состоит из намерений.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|---|---|---|
| Драйвер смены живёт вне Rust-workspace и не покрывается гейтами конституции (`cargo fmt`, `clippy`, `cargo test`) | Цикл смены — оркестрация процессов и разбор JSON, меняется каждую ночь первые недели. Держать его в бинаре хранилища значит гонять релизные гейты базы данных ради правки формулировки промпта | «`au smena run` подкомандой в том же бинаре» отвергнут: единый бинарь удобнее, но привязывает темп изменения цикла к темпу релиза хранилища, и добавляет в процесс, который открывает базу, логику запуска дочерних агентов. Компенсация: драйвер не открывает базу вовсе — все обращения через `au`, то есть код, который гейты проходит |
