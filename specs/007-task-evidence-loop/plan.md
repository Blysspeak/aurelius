# Implementation Plan: Круг «задача — работа — улика — закрытие»

**Branch**: `007-task-evidence-loop` | **Date**: 2026-08-30 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/007-task-evidence-loop/spec.md`

## Summary

Задача сегодня закрывается только тогда, когда человек вспомнит и скажет вслух. Всё остальное в
круге уже механическое: правка фиксируется хуком `edit-track`, прогон пишет артефакт
`.ulika/artifacts/*.log`, гейт считает свежесть улики позицией в журнале. Не хватает шва между
ulika и aurelius: прогон состоялся, но задача о нём не знает.

Подход: не строить новую подсистему, а связать две существующие. Времена переходов и способ
решения кладутся в уже имеющееся поле `data` узла `Task` (JSON, схема не меняется). Улика
приходит из журнала ulika — она там уже посчитана, в `state.mjs` есть `freshGreen` и `codeEdits`.
Созревание вычисляется на лету из этих двух фактов, а не хранится флагом. Предъявление вешается
на существующий хук `Stop`, где уже стоит `au judge --hook`.

## Technical Context

**Language/Version**: Rust 2021 (workspace: `aurelius-core`, `au`, `aurelius`, `aurelius-sync-server`);
Node.js ESM для обвязки ulika
**Primary Dependencies**: `rusqlite` (SQLite), `serde_json`, `chrono`, `thiserror`/`anyhow`, `clap`
**Storage**: одиночный SQLite-файл; задачи — узлы `NodeType::Task`, поля задачи живут в
`data` (JSON), статус в `data.$.status`, открытые статусы — константа `OPEN_TASK_STATUSES`
(`active,blocked,backlog`)
**Testing**: `cargo test --workspace`; интеграционные — `crates/au/tests/exit_codes.rs`;
обвязка ulika проверяется прогоном хуков на живом журнале
**Target Platform**: Windows 11 (основная), кроссплатформенный CLI
**Project Type**: CLI + MCP-сервер над локальной графовой БД
**Performance Goals**: вычисление созревания не должно заметно удлинять хук `Stop` (бюджет хука
20 с, реальная цель — десятки миллисекунд)
**Constraints**: обратная совместимость машинно-читаемой формы снапшота (её читает
`ulika/hooks/lib/au.mjs`); новые поля в `data` задачи опциональны — старые узлы без них должны
читаться
**Scale/Scope**: ~12000 узлов, 228 открытых задач в основном проекте, 19 репозиториев с журналами

## Constitution Check

*GATE: пройден до Phase 0, перепроверен после Phase 1.*

| Принцип | Как соблюдается |
|---|---|
| I. Data Durability First | Новых таблиц и миграций нет: времена и способ решения кладутся в существующее поле `data` (JSON). Старые узлы без новых ключей остаются валидными. Изъятие команд не трогает данные — удаляется код, не строки БД. |
| II. One Local File, Many Processes | Записи идут теми же путями, что уже работают под конкуренцией (`au task update`, хуки на каждую правку). Новых писателей не появляется: привязка правки к задаче пишется тем же хуком, что уже пишет след правки. |
| III. Rust Clean Code | Разбор `data` задачи — через типизированную структуру с `Option`-полями и `serde`, а не `json_extract` по месту с `unwrap`. Ошибки — `thiserror` в `aurelius-core`, `anyhow` на границе `au`. |
| IV. Surgical Simplicity | Созревание не хранится, а вычисляется: хранимый флаг требовал бы сброса при каждой правке, и рассинхрон был бы вопросом времени. Единственная активная задача переиспользует механику аренды из 006 (`lease.rs`), а не вводит вторую. |
| V. Verify Before Done | Каждая фаза закрывается тремя гейтами (`fmt`, `clippy`, `test`) плюс прогоном настоящего бинаря против живой БД — для фаз, меняющих чтение или запись задач. |
| VI. MCP Surface Stability | Изымаемые команды (`sync`, `capture`) не имеют MCP-двойников: проверено по `crates/aurelius/src/mcp/tools.rs`. Поверхность MCP растёт только аддитивно: новые поля в результатах `task_view`/`task_list`, новых обязательных параметров нет. |

**Отдельно по семверу**: изъятие CLI-команд — ломающее изменение для командной строки, хотя
поверхность MCP не затронута. Коммиты фазы G должны нести пометку ломающего изменения, чтобы
следующий релиз поднял мажор.

**Structure Decision**: правки распределены по существующим границам крейтов. Единственный новый
модуль — `crates/aurelius-core/src/tasks.rs`: типизированное представление полей задачи. Он нужен
потому, что поля лежат в свободном JSON, и без типа каждое место чтения писало бы свой
`json_extract` — ровно та россыпь, которую запрещает принцип III.

## Фазы реализации

Порядок выбран так, чтобы каждая фаза давала работающий результат сама по себе.

| Фаза | Что делает | Требования | Где |
|---|---|---|---|
| A | Времена переходов и единственная активная задача | FR-001…003, FR-031, FR-032 | `tasks.rs`, `lease.rs`, `commands.rs` |
| B | Способ решения и привязка улики | FR-004…010 | `tasks.rs`, `commands.rs`, `ulika/hooks/lib/au.mjs` |
| C | Созревание и предъявление | FR-011…016 | `aurelius-core`, хук `Stop` |
| D | Активные задачи в подаваемой памяти | FR-017…020 | `snapshot.rs` |
| E | Возврат снимка после сжатия контекста | FR-021…023 | `ulika/hooks/precompact.mjs` |
| F | Координаты секретов | FR-024…027 | `models.rs`, `commands.rs` |
| G | Изъятие мёртвых команд | FR-028…030 | `commands.rs`, `capture.rs`, README |

Фазы A и E независимы друг от друга и от остальных: E — правка одной строки в чужом репозитории,
её можно сделать первой, если нужен быстрый результат.
