## Summary

Recall сегодня отдаёт двенадцать узлов, выбранных по степени хаба и дате, потому что bm25
умирает на seed-ах (`handlers/session.rs:253`); проекты смешаны; половина записей — машинные
прогоны. Снимок на старте отвечает «что есть в проекте», а не «на чём остановились». Память не
приходит сама: агент должен позвать `memory_recall`, и он не зовёт.

Подход: ничего нового не хранить и ничего не переписывать LLM-ом. Четыре правки поверх
существующего: (1) ранжирование, отказ и рендер в `search.rs` и обработчике recall; (2) блок
«где остановились», выводимый из `act_trace` внутри `build_snapshot`; (3) один новый хук
`UserPromptSubmit` → `au recognize --hook`, только чтение, ≤ 50 токенов; (4) **отдельная
FTS5-таблица `nodes_stem_fts`** со стеммированным текстом и явной командой `au db reindex-stems` — не колонка
внутри `nodes_fts` (почему именно так — `research.md` B.1/B.4, это измерение, а не вкус). Всё
измеряется `au eval` на фикстурном дампе, число «до» снимается в первый день.

## Constitution Check

*GATE: пройден до Phase 0, перепроверить после Phase 1.*

| Принцип | Как соблюдается |
|---|---|
| I. Data Durability First | Схема узлов не меняется. `nodes_fts` не меняется: стемминг живёт в **отдельной** таблице `nodes_stem_fts`, заполняемой явной командой `au db reindex-stems` (FR-022). Пока она пуста, поиск идёт ровно как сегодня — молчаливой деградации нет по построению, а не по флагу. Откат — `DROP TABLE nodes_stem_fts`. Working state не хранится — выводится из `act_trace`. Фикстура eval — копия базы (`VACUUM INTO`, `crates/au/src/main.rs:373`), живая база при eval не открывается на запись. |
| II. One Local File, Many Processes | `au recognize --hook` открывает базу через `db::open_readonly` (`db.rs:154`, сегодня приватная — фича делает её `pub` **в фазе A**, а не в D: первый потребитель — `au eval`, который обязан открыть фикстуру только на чтение уже на первом прогоне; фаза D просто пользуется готовым), а **не** через `db::open`: `open` зовёт `ensure_wal` (`PRAGMA journal_mode=WAL`, берёт кратковременный эксклюзивный лок), ставит `PRAGMA synchronous=FULL` и прогоняет `migrate()` — то есть открывает на запись (`db.rs:96-118`). `access_count` не инкрементится (FR-014a). Единственный новый писатель — разовая переиндексация. |
| III. Rust Clean Code | Веса ранжирования — типизированная структура `RankWeights` с `Default`, не россыпь констант по месту. Множитель типа `T` — функция `match` по `&NodeType`, а не `HashMap`: `NodeType` (`models.rs:5`) выводит только `Debug, Clone, Serialize, Deserialize` — ни `Eq`, ни `Hash`, ключом карты быть не может. Провенанс читается из `Option<Confidence>` напрямую, мимо `Provenance::confidence_or_default()` (`provenance.rs:311`), который схлопывает «поля нет» и `unverified` в одно значение, а нам они нужны разными. Разбор `act_trace` — через существующие типы `trace.rs`. Ни одного `unwrap` на рантайм-пути; `expect_used` в `deny` уже стоит. |
| IV. Surgical Simplicity | Отвергнуто: эмбеддинги, новое хранилище для working state, новые хуки на `SessionStart`/`Stop`, консолидация LLM, свой токенизатор FTS5. Один новый хук, одна новая зависимость, одна новая FTS-таблица. Working state выводится, а не хранится. Третья функция порядка не заводится: `graph::by_degree_then_recency` (`graph/mod.rs:157`) остаётся как есть и продолжает кормить `au pickup` (`pickup.rs:335`, `pickup.rs:370`), где порядок по степени подграфа — заявленное намерение. Вторая копия той же формулы в `handlers/session.rs:253-257` не переезжает на неё, а **удаляется**: путь recall уходит на `rank::score`. Что возвращает `au pickup`, эта фича не меняет; перевод pickup на новый ранг — отдельная задача вне её области. |
| V. Verify Before Done | Каждая фаза закрывается `fmt`/`clippy`/`test` плюс прогоном `au eval` на фикстуре; число фазы записывается в `research.md` рядом с числом «до». Два утверждения, которые нельзя путать: **приёмка фазы F** требует числа **строго выше** числа «до» по каждому виду кейсов в отдельности (SC-002); принцип «фаза не закрыта, если её число ниже предыдущего» относится к **последующим** прогонам, уже после того как фаза закрылась, — это защита от регрессии, а не критерий приёмки. |
| VI. MCP Surface Stability | Три разные поверхности, у них разные контракты, и раньше они были свалены в одну строку. **`memory_recall`**: прежние поля JSON сохраняются; добавляются `prose`, `refused` (с `matched`/`advice`), `other_projects`. **`memory_snapshot`** (MCP): отдаёт `{project, markdown}` и **никакого `facts` не содержит вовсе** (`handlers/snapshot.rs:9-23`) — блок «где остановились» приезжает в него сам, потому что рождается внутри `graph::build_snapshot`; форма ответа не меняется. **`au snapshot --json`**: единственное место, где живёт контракт `facts[]`; добавляется поле верхнего уровня `state`. Собирается эта форма **не** `build_snapshot`, а `graph::snapshot_facts` (`graph/snapshot.rs:268`) — флаг объявлен `conflicts_with = "hook"` (`crates/au/src/main.rs:649-650`), — поэтому `state` вставляется в неё отдельно, из того же вычисления, что кормит markdown-блок. Ограничение здесь жёстче, чем «аддитивно»: тест `json_facts_shape_is_fixed_and_empty_means_nothing_to_say` (`graph/snapshot.rs:581`) сравнивает **всю** сериализованную строку побайтово с `{"project":"пусто","facts":[]}` — он не доказывает аддитивность, он её запрещает. Значит `state` обязан стоять **последним** полем `SnapshotFacts` и нести `#[serde(skip_serializing_if = "Option::is_none")]`, иначе этот тест краснеет. Новых обязательных параметров нет. |

## Phase 0 — research.md

Решения, уже принятые разведкой 2026-09-08 (вносятся как есть):

- `/clear` даёт `SessionStart` с `source=clear` — подтверждено `lib/restore.mjs:58`.
- Жёсткого бюджета у `UserPromptSubmit` нет; 200 мс — самоограничение.
- Стемминг — **не токенизатор**: токенизатор не различает точный токен и стем (FR-021), и
  Rust-API его регистрации сегодня недоступен (фичи `fts5` у rusqlite в воркспейсе нет).
  Где именно живёт стеммированный текст — колонка внутри `nodes_fts` или своя таблица — Phase 0
  закрыла измерением: **своя таблица `nodes_stem_fts`** (`research.md` B.1, B.4).
- `parseMemory()` ulika номер секции отбрасывает — блок первым.
- Источник «последнего хода» — `act_trace`, не `work_log` ulika.
- Ранг recall сегодня = degree + created_at (`handlers/session.rs:253`); bm25 не доживает.

Что должно быть снято **до первой правки поиска**. Исполнитель — фаза A целиком; раньше этот
список и таблица фаз расходились (список требовал оба числа до правки поиска, таблица отдавала
полы кейсов фазе F), теперь расхождения нет:

1. Фикстура: `au db backup` живой базы → `fixtures/eval/`, обезличивание по списку владельца.
2. **Оба пола кейсов сразу**: ≥ 30 кейсов вида `recall_top5` и ≥ 20 вида `morphology`. После
   фазы A этот набор **заморожен** — фаза F к нему кейсов этих двух видов не добавляет.
   Причина не в аккуратности: число «до», снятое на десяти кейсах, и число «после», снятое на
   тридцати, — не сравнимые величины, и SC-002 на них не проверяется.
3. Число «до» на этом замороженном наборе: доля попадания в топ-5 на `recall_top5`; доля
   непустых выдач на `morphology`.
4. Замер `au recognize` в наивной реализации (словарь + точное совпадение) на живой базе —
   чтобы знать запас до 200 мс.

### Стартовые параметры (догадки, помечены; калибруются `au eval`)

| Параметр | Старт | Основание |
|---|---|---|
| df-вето | терм в > 1 % узлов (~160) → не сущность; тема из таких термов → отказ | df(«au») = 3,5 %; порог с запасом |
| Мин. значимых термов в теме | 2, иначе отказ с советом | короткая тема = широкая |
| Нормировка bm25 | `r = \|rank\| / (\|rank\| + median\|rank\|)` внутри выдачи | FTS5 rank отрицателен и не нормирован |
| Провенанс P | measured 1.0 / reported 0.8 / inferred 0.75 / **поля нет** 0.7 / unverified 0.6 | читается из `Option<Confidence>` напрямую: «поля нет» (76 % базы) и явный `unverified` — разные утверждения, и `confidence_or_default()` (`provenance.rs:311`) их схлопывает, поэтому он здесь не зовётся. Порядок measured → reported → inferred — это ранжирование, а не порядок объявления enum (`provenance.rs:37-47` объявляет `Inferred` раньше `Reported`; объявление не ранг) |
| Свежесть R | `1 / (1 + age_days / 180)` | было 90 — арифметически ломало FR-007b, см. проверку ниже |
| Обращения A | `1 + 0.15 · min(ac, 20) / 20` | сигнал самоподкреплён (recall сам инкрементит) |
| Тип T | decision/solution 1.0, concept 0.95, problem 0.9, task 0.85, file 0.5, **session/run/work_log 0.15**; **всё, что не названо, — 0.7** | было 0.3 — не перебивало свежесть. `run` существует только как `NodeType::Custom("run")` (в `KNOWN` его нет, `models.rs:41-62`), но это машинный узел и множитель у него машинный. | Итог | `score = r · P · R · A · T` — **ровно пять множителей**; степени узла среди них нет | мультипликативно: unverified с идеальным bm25 не перебивает measured. Проверено в дереве — степень узла не участвует ни в видимости, ни в порядке: видимость задают рёбра и потолки обхода, а `subgraph_degree` считается уже после обхода и кормит только сегодняшний порядок, который эта спека убирает |

| Бюджеты | узнавание ≤ 50 токенов, факты ≤ 200, блок «где остановились» ≤ 300 | спека |
| Текущий момент | параметр `now`, не `Utc::now()` внутри `score` | иначе `au eval` недетерминирован: тот же файл кейсов даёт разные числа назавтра |

**Проверка арифметикой (почему 180 и 0.15, а не 90 и 0.3).** Берём худший для FR-007b случай:
bm25 равен, провенанс равен — «поля нет», `P = 0.7` у обоих (76 % базы). Сравниваем годовое
`decision` и вчерашний `work_log`:

| Параметры | Годовой `decision` | Вчерашний `work_log` | Кто выигрывает |
|---|---|---|---|
| было: τ = 90, T = 0.3 | `0.7 · R(365)=0.198 · 1.0` = **0.139** | `0.7 · R(1)=0.989 · 0.3` = **0.208** | машина, в 1,5 раза — прямое нарушение FR-007b |
| стало: τ = 180, T = 0.15 | `0.7 · R(365)=0.330 · 1.0` = **0.231** | `0.7 · R(1)=0.994 · 0.15` = **0.104** | решение, в 2,2 раза |

Одной правки не хватило бы: при τ = 180 и старом `T = 0.3` получилось бы 0.231 против 0.209 —
преимущество в 1,1 раза, то есть внутри шума bm25. Обе величины двигаются вместе. Запас: при
`T = 0.15` годовое решение обходит вчерашний `work_log` уже при τ > 63 дней, так что 180 — не
край, а середина рабочего диапазона.

Оба числа остаются **догадками** и калибруются `au eval` (`research.md` C — чем каждую
опровергнуть).

**Три обязательства, которые фазы обязаны выполнить, иначе `cargo test --workspace` краснеет или

1. **Фаза B, компаратор — и чего она делать НЕ должна.** `graph::by_degree_then_recency`

   степени подграфа — заявленное намерение, а не случайность. Поэтому копия из
   `handlers/session.rs` **удаляется**, а не переезжает на общую функцию: путь recall уходит
   прямо на `rank::score`,
   `by_degree_then_recency` остаётся нетронутой и продолжает кормить pickup. Прежняя редакция
   плана предлагала обратный порядок работ («сначала `handlers/session.rs` зовёт общую функцию, потом эта
   одна функция переводится на `rank::score`») — он молча менял бы и выдачу `au pickup`.
   Что возвращает `au pickup`, эта фича не меняет; перевод pickup на новый ранг — отдельная
   задача **вне** её области. Третья функция порядка не заводится.
2. **Фаза C, `pickup.rs`.** `au pickup --project <P> --json` уже пересобирает рабочее состояние
   после разрыва контекста: якорь → хвост последней сессии → записи, ранжированные степенью
   подграфа (доккомментарий `pickup.rs:1-19`). Блок «где остановились» обязан быть с ним сверен —

   рабочего состояния в репозитории быть не должно. Сверка — чтение, а не правка: порядок и
   состав, которые pickup отдаёт, в этом цикле остаются прежними.
3. **Фаза D, манифест.** `crates/au/tests/plugin_manifest.rs:157` —

## Complexity Tracking

Нарушений конституции нет. Единственное место, требующее оговорки: появляется новая виртуальная
таблица `nodes_stem_fts`. Out of Scope спеки запрещает «новые хранилища, таблицы **вне
FTS-индекса**, миграции схемы узлов» — FTS5-таблица под эту формулировку не подпадает, но это
чтение буквы, и оно признаётся вслух.

Почему не колонка внутри `nodes_fts`, как план говорил раньше: у внешнеконтентной FTS5-таблицы
колонка, которой нет в `nodes`, **измеримо** ломает и `INSERT INTO nodes_fts(nodes_fts)
VALUES('rebuild')`, и любое чтение колонок (`no such column: T.label_stem`) — `research.md` B.1.
Форма без этой поломки требует `ALTER TABLE nodes`, то есть ровно той «миграции схемы узлов»,
которую спека вынесла из области. Отдельная таблица платит местом на диске (прирост —
НЕ ИЗМЕРЕНО) и вторым MATCH на запрос, а покупает: FR-021 по построению (точное и стеммированное
совпадение — два разных множества, а не один подобранный вес), FR-022 даром (пустая таблица =
сегодняшнее поведение), рабочий `'rebuild'` у боевого индекса и откат одной строкой `DROP TABLE`.

Версия схемы в `db.rs` поднимается 14 → 15 (`SCHEMA_VERSION`, `db.rs:8`); цепочка `db::migrate`
(`db.rs:464`) принимает пятнадцатую ступень без переделки механизма; старая база читается до
первого `au db reindex-stems`.

Имя команды закрыто, а не оставлено фазе E: **`au db reindex-stems`**. `au reindex` сегодня
означает «проиндексировать исходники проекта в граф» (`commands.rs:1113`) — операция другой
природы над другим объектом, и вешать на неё флаг значило бы склеить два разных смысла в одном
имени. `au db` — существующая группа обслуживания базы (`crates/au/src/main.rs:363` —
`DbAction::Check`, `DbAction::Backup`), пересборка индекса принадлежит ей. В этом цикле команда
на хуки не вешается, поэтому список подкоманд `plugin_manifest.rs:157` она не задевает.
