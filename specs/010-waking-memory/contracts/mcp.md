## 1. `memory_recall` сегодня

### 1.1 Объявление инструмента

`crates/aurelius/src/mcp/tools.rs:332-350`. Параметров ровно два: `topic` (обязательный, строка) и
`depth` (целое, умолчание 2). **Параметра `project` в схеме нет.** Схема — не декорация: заслонка
`params::validate` (`crates/aurelius/src/mcp/params.rs:123`) собирает белый список имён из
`inputSchema` и отвечает `isError: true` на любое имя вне него. Значит любой новый параметр
добавляется ровно в одном месте — в `tools.rs`, — и белый список расширяется сам.

### 1.2 Путь запроса

`crates/aurelius/src/mcp/handlers/session.rs:201-285`:

1. `graph::context_with_report_seeded(&conn, topic, depth, graph::RECALL_SEEDS)` — 12 FTS-посевов
   (`traverse.rs:63`), затем BFS. Потолок обхода — 200 узлов (`traverse.rs:19`), глубина зажата
   тройкой (`traverse.rs:25`).
2. **После** обхода, по рёбрам уже готового результата, считается степень каждого узла
   (`handlers/session.rs:222-226` — построчная копия `graph::subgraph_degree`, `graph/mod.rs:145`). На
   то, кто попал в результат, она повлиять не может: обход к этому моменту уже закончился.
3. Отсев: `NodeType::Skill` и `NodeType::Project` выбрасываются; `MemoryKind::Episodic` уходит в
   хвост `recent`, остальное — в `knowledge`.
4. Порядок — вот он целиком, `handlers/session.rs:253-259`:

```rust
    let rank = |a: &&aurelius_core::models::Node, b: &&aurelius_core::models::Node| {
        let da = degree.get(&a.id).copied().unwrap_or(0);
        let db = degree.get(&b.id).copied().unwrap_or(0);
        db.cmp(&da).then(b.created_at.cmp(&a.created_at))
    };
    knowledge.sort_by(rank);
    episodic_tail.sort_by(rank);
```

   bm25 участвует только в выборе 12 посевов внутри `search()` и до этой сортировки не доживает.
5. Срез: `RECALL_LIMIT = 12` (`handlers/session.rs:14`), `RECALL_TAIL_LIMIT = 2` (`handlers/session.rs:18`).
6. **Запись при чтении**: `handlers/session.rs:264-269` зовёт `graph::touch_node` на каждый показанный узел —
   инкремент `access_count`, best-effort, ошибка только логируется.

Тот же компаратор вынесен в `graph/mod.rs:157-165` как `by_degree_then_recency`. Сравнено
построчно: замыкание `handlers/session.rs:253` и функция в `graph/mod.rs` — одно и то же тело, дважды.
Саму функцию сегодня зовёт только `au pickup` — два места, `graph/pickup.rs:335,370`, где
порядок по степени в подграфе и есть заявленное назначение.

Что с этим делает спека, сказано здесь целиком, чтобы следствие не пришлось выводить самому:
**путь recall переходит на `rank::score`, а `by_degree_then_recency` остаётся как есть**.
`handlers/session.rs` перестаёт объявлять своё замыкание и сортирует `rank::score`; третьего
экстракта-компаратора не заводится — общей функцией служит сам `rank::score`. Вместе с
замыканием с пути recall уходит и подсчёт степени (`handlers/session.rs:222-226`): в произведении её
нет, а больше её там некому читать. `au pickup` в этом цикле отдаёт ровно то же, что и сегодня;
его перевод — отдельная задача **вне** этой фичи (см. §4 п. 16). Дубль компаратора при этом
всё равно исчезает: не потому, что обе стороны перешли на новое, а потому, что одна из двух
копий удаляется вовсе.

### 1.3 Форма ответа

Дословно, `handlers/session.rs:271-285`:

```json
{
  "topic": "au",
  "knowledge": [ /* до 12 узлов, форма node_recall */ ],
  "recent":    [ /* до 2 узлов, форма node_recall */ ],
  "shown": 12,
  "matched_knowledge": 162,
  "matched_recent": 3,
  "total_graph_nodes": 200,
  "truncation": {
    "truncated": true,
    "hidden_nodes": 760,
    "truncated_at_depth": 2
  }
}
```

Числа в примере — живой вывод `memory_recall(topic="au")` из разведки 2026-09-08 (162 совпадения,
760 узлов за кадром, показано 12); `matched_recent`, `total_graph_nodes` и `truncated_at_depth` в
том выводе не зафиксированы и здесь приведены как форма, а не как измерение.

Элемент `knowledge[]` / `recent[]` — `node_recall` (`crates/aurelius/src/mcp/handlers/mod.rs:239-259`),
ровно восемь полей:

| Поле | Тип | Что это |
|---|---|---|
| `id` | string (UUID) | идентификатор узла |
| `type` | string | тип узла (`decision`, `problem`, `file`, …) |
| `label` | string | метка узла, без обрезки |
| `claim` | string \| null | утверждение из `data.claim` |
| `window` | string \| null | окно 200 символов вокруг совпадения — **только когда `claim` пуст** (`RECALL_WINDOW`, `handlers/mod.rs:233`) |
| `subject` | string \| null | предмет из провенанса |
| `confidence` | string | `measured` \| `reported` \| `inferred` \| `unverified`; отсутствие читается как `unverified` |
| `created_at` | string | RFC 3339 |

Тела узла (`note`, `data`) `memory_recall` не отдаёт никогда — это осознанное решение, записанное
в доккомментарии `node_recall`.

### 1.4 Чего в `memory_recall` нет сегодня

- `unmatched_terms` и `query_hint` — это поля **`memory_search`** (`handlers/crud.rs:78-87`), не
  recall. FR-023 («подсказка префикса остаётся») относится к `memory_search`; в `memory_recall`
  подсказки не было и не появляется.
- Фильтра секретов. `search_ranked` отсеивает `secret::is_secret_ref` на всех трёх своих путях, но
  `traverse.rs` фильтра не содержит вовсе: узел-координата, до которого BFS дошёл **по ребру**, а
  не посевом, попадает в `knowledge` как обычный `Config`. См. OQ-3.
- Ограничения по проекту. Именно поэтому в живом выводе `[nexalix]` и `[aurelius]` шли вперемешку.

## 2. `memory_recall` после спеки

### 2.1 Отказ на слишком широкой теме (FR-006, SC-001)

**Отказ — это успешный результат, а не ошибка.** Обработчик, вернувший `Err`, оборачивается в
`{"content":[{"type":"text","text":"Error: …"}],"isError":true}` (`mcp/mod.rs:182-191`) — структура
диагноза при этом теряется в текстовом блобе, и вызывающий не может отличить «тема широкая» от
«база не открылась». Поэтому отказ идёт обычным `Ok(json)`, а признаком служит поле `refused`.

Два повода отказать:

| `reason` | Условие | Стартовый порог |
|---|---|---|
| `topic_too_broad` | хотя бы один терм темы встречается более чем в N % живых узлов | N = 1 % (~160 узлов при 16 333 живых) |
| `topic_too_narrow` | значимых термов в теме меньше двух (после отсева термов с df выше вето) | 2 терма |

**Порядок проверки задан здесь, а не оставлен реализации: `topic_too_broad` проверяется первым и
побеждает, когда истинны оба.** У темы «au» они истинны оба и есть: терм `au` стоит выше вето
(3,5 %), а после его отсева значимых термов остаётся ноль — то есть меньше двух. Ответить
«тема слишком узкая» на тему из одного слишком широкого слова значило бы сделать верный вывод из
неверного шага и назвать причину, которую нечем исправить.

Значимый терм — то, что `fts::parse` (`crates/aurelius-core/src/fts.rs:46-86`) положил в `terms`,
за вычетом термов с df выше вето. Собственного стоп-листа у базы нет и не заводится: стоп-слово
вычисляется по df, а не хранится (Key Entities спеки).

Считать df есть чем: `graph/search.rs:214-230` уже спрашивает индекс о терме запросом
`SELECT 1 FROM nodes_fts … MATCH ?1 … LIMIT 1`. Вето — тот же запрос с `COUNT(*)` вместо `SELECT 1`
и без `LIMIT`. Решение принимается **до** обхода, поэтому `matched` в отказе — это число узлов
индекса по терму, а не `matched_knowledge` после BFS: путать их нельзя, они меряют разное.

Форма отказа. Все прежние поля на месте и пусты — старый потребитель, читающий `knowledge`, получает
пустой массив, а не отсутствующий ключ:

```json
{
  "topic": "au",
  "refused": {
    "reason": "topic_too_broad",
    "matched": 570,
    "terms": [
      { "term": "au", "df": 0.035, "nodes": 570 }
    ],
    "advice": "тема слишком широкая: терм «au» встречается в 3,5 % узлов и тему не сужает. Второе слово рядом не поможет — термы склеиваются через OR, поэтому «au judge» шире, чем «judge». Замените широкий терм парой узких: «стемминг recognize», «judge фикстура». Либо сузьте область: --project aurelius."
  },
  "knowledge": [],
  "recent": [],
  "shown": 0,
  "matched_knowledge": 0,
  "matched_recent": 0,
  "total_graph_nodes": 0,
  "truncation": { "truncated": false, "hidden_nodes": 0, "truncated_at_depth": null },
  "prose": "",
  "project": "aurelius",
  "other_projects": 0
}
```

Про числа примера: `df = 0.035` — измеренная величина (разведка 2026-09-08). `nodes: 570` — это
3,5 % от 16 333 живых узлов, то есть арифметика по двум измеренным числам, **не отдельное
измерение**; точное число берётся из базы в момент отказа.

**Текстом совета владеет `contracts/cli.md` §4.** Здесь он **процитирован**, дословно, вплоть до
подстроки «не сужает»: именно её нормативный кейс `refuse-topic-au` проверяет через
`advice_contains`. Разошлись — прав `contracts/cli.md` §4, и правится этот файл;
`contracts/eval-cases.md` цитирует тот же источник, а не этот документ (кольцевых указателей
«tasks → eval-cases → cli» больше нет). Правило, из которого совет выведен: вето стоит на df
**отдельного** терма, а `fts::parse` склеивает слова через `OR` (`fts.rs:80-84`), поэтому второе
слово рядом делает выдачу **шире**, а не уже. Отсюда обе половины совета: широкий терм надо
**заменить**, а не разбавить, и замена обязана сама пройти детектор, из которого совет и вышел —
совет, ведущий в тот же отказ, хуже молчания.

**Правило порождения подсказок, из-за которого они — пары, а не одиночные слова.** Каждая
предложенная тема собирается **только из термов ниже вето** и несёт их **не менее двух**: одно
узкое слово само упёрлось бы в `topic_too_narrow` («значимых термов меньше двух», см. таблицу
выше), то есть совет вёл бы в другой отказ вместо ответа. Хвост `--project aurelius` из-под этой
проверки выведен намеренно: это сужение **области**, а не тема, и через детектор тем он не
проходит вовсе. Слова в примере взяты как форма: их df на живой базе не снят (фаза A), и
подсказка, вето не прошедшая, из совета выбрасывается — вместе со вторым словом своей пары, а не
в одиночку, иначе останется тема из одного терма. Область названа флагом `--project aurelius`,
потому что текст один на CLI и MCP; в `memory_recall` то же сужение даёт необязательный параметр
`project` (§2.4).

Краевой случай спеки (терм одновременно стоп-слово и имя сущности, `guard`): `advice` дописывает
хвост «если ты про проект Guard — укажи `project`». Условие — имя терма совпало с меткой узла типа
`project`; проверка стоит один запрос по метке.

`refused` отсутствует (или `null`) в любом нормальном ответе. Потребитель отличает отказ от пустоты
по наличию `refused`, а не по `shown == 0`: пустая выдача по узкой теме — это не отказ.

### 2.2 Аддитивные поля (FR-012)

Ни одно существующее поле не удаляется, не переименовывается и не меняет тип. Причина — не вкус:
`memory_recall` читает MCP-клиент Claude Code, и молчаливое переименование обнаруживается только
тем, что модель перестаёт видеть память.

Верхний уровень ответа:

| Поле | Тип | Аддитивность | Требование | Что несёт |
|---|---|---|---|---|
| `refused` | object \| null | **аддитивное** | FR-006 | `reason`, `matched`, `terms[]`, `advice` — см. 2.1 |
| `prose` | string | **аддитивное** | FR-010, FR-012 | вся выдача прозой, по строке на узел; пустая строка при отказе |
| `project` | string \| null | **аддитивное** | FR-009 | область, которая фактически применилась; `null` = глобально |
| `other_projects` | integer | **аддитивное** | FR-009 | сколько узлов других проектов осталось за кадром |

`refused`, `prose` и `other_projects` названы планом (Constitution Check, п. VI). `project`
добавлено здесь: FR-009 требует «ограничиться проектом текущего каталога», а ответ, который не
называет применённую область, невозможно ни проверить в `au eval`, ни отладить, когда каталог
опознан не тем проектом. Помечено как расширение плана.

Внутри `knowledge[]` и `recent[]`, дополнительно к восьми полям `node_recall`:

| Поле | Тип | Аддитивность | Требование | Что несёт |
|---|---|---|---|---|
| `score` | number | **аддитивное** | FR-007 | итог `r · P · R · A · T` |
| `signals` | object | **аддитивное** | FR-007, FR-026 | `{ "bm25": r, "provenance": P, "freshness": R, "access": A, "type": T }` — множители по отдельности |
| `project` | string \| null | **аддитивное** | FR-016, edge case «два проекта в одном сообщении» | метка проекта узла |

`signals` — не украшение: FR-026 требует от отчёта eval показывать «что ожидалось и что пришло», а
по одному итоговому `score` нельзя сказать, узел просел по свежести или по типу. Это же поле —
единственный способ калибровать веса, не пересобирая бинарник с отладочной печатью.

Имена `bm25`, `provenance`, `freshness`, `access`, `type` соответствуют строкам таблицы «Стартовые
параметры» плана (`r`, `P`, `R`, `A`, `T`).

**Ключей в `signals` ровно пять, и `degree` среди них нет.** И дело не в том, что связность
«осталась в другом месте»: **степень узла не участвует ни в видимости, ни в порядке: видимость
задают рёбра и потолки обхода, а `subgraph_degree` считается уже после обхода и кормит только
сегодняшний порядок, который эта спека убирает** (FR-007a). Проверено по коду: `walk`
(`crates/aurelius-core/src/graph/traverse.rs:105-163`) степень не считает и не читает, посевы
из `search()` кладутся безусловно — узел нулевой степени показывается; `subgraph_degree`
(`graph/mod.rs:145`) считается по рёбрам готового результата. Это часть контракта провода, а не
деталь реализации — потребитель, увидевший шестой ключ, обязан считать это регрессией.
Проверяется тем же тестом, что и в `data-model.md`, и тест **односторонний**: два узла с равными
пятью множителями и разной степенью обязаны дать равный `score`. Про состав выдачи он не
утверждает ничего — состав решают рёбра и два потолка обхода.

Значение `bm25` у узла, до которого дошли обходом, а не посевом FTS, — фиксированное нейтральное
`0.5` (`RankWeights::r_traversed`), потому что bm25 у него не существует: посевов
`RECALL_SEEDS = 12`, а в выдаче до 200 узлов. Полный разбор и три отвергнутых варианта — в
`data-model.md`, раздел 1. В JSON это обычное число, отличить его от заработанного нельзя и не
нужно.

### 2.3 Проза (FR-010, FR-011)

`prose` — текст, который читает модель. Одна строка на узел, одна форма для всех узлов независимо
от того, что у узла заполнено:

```
[decision] aurelius · 2026-09-05 — карточка rust-clean-code не восстанавливается; правило держат
    воркспейсные линты unwrap_used/expect_used = deny
[problem] aurelius · 2026-08-30 — обход глубины 2 от посева уходит в чужие проекты через узел-хаб
```

Правила:

- Порядок строк = порядок `knowledge`, затем `recent`. Группировка по типу порядок внутри группы не
  сбрасывает (FR-008).
- Текст берётся так же, как его берёт `push_facts` снимка: `claim`, иначе `note`, иначе `label`.
  Различие `window` и `claim` в прозе не видно вовсе — это и есть «одна строка одной формы»
  (FR-010, история 2, сценарий 5). В JSON поля `claim` и `window` при этом остаются как были.
- **UUID в прозе нет.** Поле `id` остаётся в JSON — за телом узла ходят по нему.
- Наносекунд нет: дата в прозе — `YYYY-MM-DD`. Поле `created_at` в JSON остаётся полным RFC 3339.
- Обрез по границе слова — существующей `graph::clip` (`graph/snapshot.rs:38`), которая уже режет по
  пробелу и ставит многоточие.
- Запись, от которой после обреза не осталось ни одного целого слова, **не попадает ни в `prose`,
  ни в `knowledge`** (FR-011). Иначе счётчик `shown` врал бы: показано 12, читаемых 9.
- Координаты секретов не попадают в `prose` — тем же `secret::is_secret_ref`, что применяют снимок
  (`graph/snapshot.rs`, `layer`) и поиск (`search_ranked`).

### 2.4 Область проекта (FR-009)

Выдача одного проекта. Узлы других проектов не показываются, но их число называется в
`other_projects` — «за кадром 40 узлов других проектов» честнее, чем тишина.

- Явный `project` в параметрах — новый **необязательный** параметр в `inputSchema` `memory_recall`.
  Обязательных параметров не прибавляется (Constitution Check, п. VI).
- Без явного `project` область берётся из текущего каталога. Механизм для этого в MCP-сервере уже
  есть: `handlers/status.rs:131` и `handlers/crud.rs:315` читают `std::env::current_dir()`. Совпадает
  ли cwd MCP-сервера с каталогом проекта владельца во всех режимах запуска клиента — **не измерено**,
  см. OQ-1.
- Предикат принадлежности берётся готовый: `project_scope_sql` (`graph/search.rs:307`) считает и
  метку `[проект] …`, и ребро в обе стороны при любом типе связи. Второй копии правила быть не
  должно — она разошлась бы молча.

## 3. Снимок

### 3.1 Как выглядит сегодня

Две формы, один сборщик `gather()` — чтобы markdown и JSON не разошлись.

**`au snapshot --json` и `memory_snapshot`.** `SnapshotFacts` (`graph/snapshot.rs:153-156`):
`{ "project": string|null, "facts": [Fact] }`. `Fact` (`graph/snapshot.rs:128-145`) — **пять** полей, не
три:

| Поле | Тип | Что это |
|---|---|---|
| `kind` | string | `userfact` \| `active_task` \| `task` \| `problem` \| `obligation` \| `session` \| `decision` \| `concept` \| `skill` \| `digest` |
| `text` | string | полный текст, без бюджетной обрезки |
| `at` | string \| null | RFC 3339, `updated_at` узла; `null` у обязательств |
| `confidence` | string | `measured` \| `reported` \| `inferred` \| `unverified` |
| `stale` | string \| null | приписка «старше N дней — перепроверь …» |

Спека (FR-002b) называет только `kind`/`text`/`at`. `confidence` и `stale` существуют в коде и точно
так же не трогаются — перечислены здесь, чтобы отсутствие в спеке не прочли как разрешение их
переставить.

`memory_snapshot` (`handlers/snapshot.rs:9-24`) markdown-only: отдаёт
`{ "project": …, "markdown": … }`; поля `facts` у него нет. Машинную форму отдаёт только CLI
(`au snapshot --json`, `commands.rs:2711-2735`).

**Markdown.** `build_snapshot` (`graph/snapshot.rs:299-373`): шапка `# Память Aurelius · <проект> · <ts> UTC`,
затем массив из **восьми** секций с захардкоженными заголовками — `1 · Владелец`,
`2 · В работе (задачи и открытые проблемы)`, `3 · Давление (незакрытые обязательства)`,
`4 · Последние сессии`, `5 · Решения и знания`, `6 · Приёмы`, `7 · Архив`, `8 · Дистиллят`. Секция с
пустым телом не печатается (`if body.is_empty() { continue; }`). Бюджеты слоёв — константы
`B_IDENTITY`=600, `B_WORKING`=1000, `B_EPISODIC`=800, `B_SEMANTIC`=900, `B_PROCEDURAL`=500,
`B_DIGEST`=500 символов (`graph/snapshot.rs:19-24`), сумма — **4300**
(600+1000+800+900+500+500). Доккомментарий над этими константами
(`graph/snapshot.rs:18`) округляет её до «~4500»; в арифметике ниже берётся 4300, потому что
складываются сами константы, а не их пересказ.

Маркеры пустоты, на которые смотрит потребитель, живут в двух местах:
`EMPTY_DIGEST = "Хвостов нет — чисто."` (`graph/snapshot.rs:163`) на стороне aurelius и на стороне ulika —
`SERVICE = /архив|дистиллят/i`, `EMPTY_LINE = /^(хвостов нет|чисто|пусто|—)\b/i`
(`ulika/hooks/lib/brief.mjs:86-87`).

### 3.2 Что добавляется: блок `state` (FR-002b)

Верхнеуровневое поле `state` в `SnapshotFacts`, **после** `facts`, чтобы префикс сериализации у
существующих потребителей не сдвинулся:

Форма ниже — не предложение, а сериализация `WorkingState` из `data-model.md` §2 через
`serde::Serialize`: те же имена полей, тот же порядок объявления, та же необязательность. Второй
формы у этого блока нет.

```json
{
  "project": "aurelius",
  "facts": [ /* без изменений */ ],
  "state": {
    "project": "aurelius",
    "branch": "feat/contour-wave-1",
    "active_task": {
      "id8": "3f8945a0",
      "label": "[aurelius] свести recall на честный ранг",
      "status": "active",
      "activated_at": "2026-09-07T18:02:11.004Z",
      "not_the_last_worked": false
    },
    "decisions": [
      {
        "id8": "ec4556a1",
        "kind": "decision",
        "text": "[decision] aurelius · 2026-09-05 — карточка rust-clean-code не восстанавливается",
        "at": "2026-09-05T11:20:03.881Z"
      }
    ],
    "blockers": [
      {
        "id8": "c7c12d16",
        "kind": "problem",
        "text": "[problem] aurelius · 2026-08-30 — обход глубины 2 уходит в чужие проекты через узел-хаб",
        "at": "2026-08-30T09:41:55.612Z"
      }
    ],
    "last_turn": {
      "kind": "traced",
      "session_id": "02a8c0aa-9022-40c0-b310-96fecfe2f804",
      "at": "2026-09-08T09:14:22.481Z",
      "age_days": 0,
      "tool_calls": 37,
      "files": ["crates/aurelius-core/src/graph/crud.rs", "crates/aurelius-core/src/secret.rs"],
      "last_error": null,
      "scope": "project_path"
    }
  }
}
```

Значения в примере — форма, а не измерение: UUID и метки взяты правдоподобные, ни одно число
здесь не снято с базы.

**`last_turn` — размеченное объединение, а не объект с флагом.** Ключ `kind` внутри `last_turn`
принимает ровно три значения, и они не сводятся к булеву:

| `kind` | Когда | Что несёт |
|---|---|---|
| `traced` | последняя группа строк `act_trace` с одним `session_id` найдена | `session_id`, `at`, `age_days`, `tool_calls`, `files[]`, `last_error`, `scope` |
| `untraced` | ходы были, но ни одного tool-call: следа нет | `at` (из последнего узла `Session` проекта; может быть `null`), `age_days` (может быть `null`) |
| `none` | по проекту нет ни одного хода | ничего, кроме `kind` |

Различие `untraced` и `none` обязательно, и вот почему оно не косметика. Сценарий приёмки
истории 1 требует, чтобы блок **назвал ход и пометил его неизвестным**, а не выдумал содержание;
сценарий FR-005 требует, чтобы при полном отсутствии ходов блок **не рендерился вовсе**. Форма с
одним булевым `known` эти два случая не различает: `known: false` пришлось бы печатать и там, где
печатать нечего. `scope` (`project_path` | `unattributed`) отвечает на отдельный вопрос — чем
доказана принадлежность хода проекту (`act_trace` колонки `project` не имеет, `db.rs:830`).

- `state` **аддитивно** и **опционально**: когда состояния нет (по проекту ни одного хода, FR-005),
  поле не сериализуется вовсе — `#[serde(skip_serializing_if = "Option::is_none")]`. Это не
  косметика: тест `json_facts_shape_is_fixed_and_empty_means_nothing_to_say`
  (`graph/snapshot.rs:581-594`) сверяет **всю строку** сериализации с `{"project":"пусто","facts":[]}`, и
  безусловное `"state":null` его уронит. С пропуском пустого поля тест остаётся зелёным как есть —
  и продолжает стеречь ровно то, ради чего написан.
- `branch` — `null`, когда каталог не репозиторий или HEAD отделён (edge case спеки), не ошибка.
- `active_task` — `null`, когда активной задачи нет. `id8` — первые 8 символов UUID, как в
  `pickup.rs`; полный UUID в блоке не печатается, за телом ходят `au recall <id8>`.
- Элементы `decisions[]` и `blockers[]` — объекты, а не строки: `text` уже отрендерен
  `render::one_line(node)`, а `id8`/`kind`/`at` рядом с ним нужны, чтобы `au eval` мог судить
  кейс `snapshot_contains` по идентификатору, а не по подстроке.
- `age_days` у `traced` есть всегда; текстовая пометка давности («последняя работа — 9 дней
  назад») — дело markdown-рендера, в JSON её нет: потребитель считает сам по `age_days`.
- Состав полей `state` спекой пофиксирован по смыслу (Key Entities «Working State»: последний ход,
  ветка, активная задача, три решения, блокеры, давность); имена ключей нормативны в
  `data-model.md` §2.

**Где этот блок появляется — две точки вставки, а не одна.** Проверено по коду, который печатает
машинную форму: `au snapshot --json` собирается **не** `build_snapshot`, а `graph::snapshot_facts`
(`graph/snapshot.rs:268`) — ветка `if json_out { … return … }` (`commands.rs:2731`) стоит раньше вызова
`build_snapshot` (`commands.rs:2734`) и до него не доходит. Отсюда:

- `build_snapshot` (`graph/snapshot.rs:299`) закрывает **три markdown-формы разом**:
  `au snapshot --project <p>`, `au snapshot --hook` и MCP-инструмент `memory_snapshot`
  (`handlers/snapshot.rs:22`). Первая секция появляется во всех трёх одной правкой.
- машинная форма получает поле `state` **отдельной вставкой в `snapshot_facts`**, из того же
  вызова `snapshot::working_state`. Одно вычисление состояния, две точки вставки; второй
  формулы состояния не заводится, иначе markdown и JSON разойдутся молча.

Обе формы читает ulika, и обе — **без** `--hook`: `au snapshot --project <p>`
(`ulika/hooks/lib/restore.mjs:185`) и `au snapshot --project <p> --json` (`ulika/hooks/lib/brief.mjs:191`). Привязывать доставку
к флагу `--hook` нельзя ещё и потому, что детектор
ulika — регулярка по границе слова `AU_SNAPSHOT_RE = /(^|[\s/\\])au(\.exe)?\s+snapshot\b/`
(`ulika/hooks/lib/restore.mjs:91`), флага в ней нет вовсе, а сама строка `au snapshot --hook` в рабочем дереве
этой ветки из `plugin/hooks.json` удалена (установленный на машине плагин 3.4.4 её ещё несёт —
то есть ответ «зарегистрирован?» зависит от того, куда смотреть). Вдобавок `--json` и `--hook`
объявлены `conflicts_with` (`crates/au/src/main.rs:649-650`) — «блок в `--hook`» и «`state` в `--json`»
физически не один вызов.

**Когда владелец его увидит.** Только на старте сессии и на `/clear`:
`RESTORE_ON = new Set(['clear', 'startup'])` (`ulika/hooks/lib/restore.mjs:58`). `compact` и `resume` исключены
там намеренно — у компакции есть своя сводка той же сессии, а возобновление держит контекст в
окне. После `/compact` и после `resume` блок не показывается, и это вне области фичи.

`memory_snapshot` (MCP) остаётся markdown-only: `state` внутрь markdown уже вошёл первой секцией,
второй копией в JSON он там не нужен, а `facts` у этого инструмента и сегодня нет.

### 3.3 Что добавляется: первая секция markdown (FR-002c)

Новая секция идёт **первой**, в том же формате `## N · Название`, номера остальных сдвигаются на
единицу: `1 · Где остановились`, далее `2 · Владелец` … `9 · Дистиллят`.

Почему это безопасно и что именно нельзя сломать:

- `parseMemory` ulika (`ulika/hooks/lib/brief.mjs:95-118`) разбирает заголовок регуляркой
  `/^##\s*(?:\d+\s*·\s*)?(.+?)\s*$/` — номер **опционален**, сдвиг нумерации она не заметит.
  Подтверждено чтением кода, не только словами плана.
- Заголовок новой секции не должен попадать под `SERVICE = /архив|дистиллят/i`, а её первая строка —
  под `EMPTY_LINE = /^(хвостов нет|чисто|пусто|—)\b/i`. «Где остановились» и строка, начинающаяся с
  проекта или ветки, обоим условиям не соответствуют. Промах здесь стоит дорого не выдачей, а
  диагнозом: ulika считает раздел «полезным» именно по этим двум регуляркам и на их основании
  печатает «каналы разошлись».
- Пустой блок не рендерится (FR-005) — существующее правило `if body.is_empty() { continue; }`
  делает это само, отдельного кода не нужно.
- Формат строк внутри блока — `- …`, как во всех секциях: `parseMemory` снимает маркер списка
  (`raw.replace(/^[-*]\s*/, '')`).
- **Бюджет.** ulika режет markdown на 8000 символах (`MAX_SNAPSHOT`, `ulika/hooks/lib/restore.mjs:45`)
  и молча теряет хвост — последним стоит `9 · Дистиллят`. Сумма бюджетов слоёв сегодня **4300**
  символов, блок добавляет ≤ 300 токенов (FR-001). Зазор до потолка — 8000 − 4300 = **3700
  символов**, и это арифметика по двум константам, а не измерение: бюджеты — потолки слоёв, а не
  длина реального снимка, которая почти всегда меньше. Настоящий запас **не измерен** — снимается
  в фазе C вместе с проверкой «`au snapshot --project <фикстура>` начинается с блока ≤ 300
  токенов».
  Флага `--hook` в этой проверке нет намеренно: ulika читает снимок именно без него
  (`ulika/hooks/lib/restore.mjs:185`), и проверять надо тот вызов, который случится, а не тот, который
  красивее звучит.

## 4. Что гарантированно не меняется

Список закрытый. Всё, чего в нём нет, тоже не меняется без правки этого файла.

**`memory_recall`:**

1. Поля `topic`, `knowledge`, `recent`, `shown`, `matched_knowledge`, `matched_recent`,
   `total_graph_nodes`, `truncation.{truncated,hidden_nodes,truncated_at_depth}` — имена, типы,
   смысл.
2. Восемь полей элемента `node_recall`: `id`, `type`, `label`, `claim`, `window`, `subject`,
   `confidence`, `created_at`. В частности `window` не исчезает и не сливается с `claim`: FR-010
   унифицирует **рендер**, не хранение и не JSON.
3. `created_at` остаётся полным RFC 3339 с наносекундами.
4. `RECALL_LIMIT = 12` и `RECALL_TAIL_LIMIT = 2` — потолки выдачи. Ранг меняет, кто попадёт в
   двенадцать, не сколько их.
5. Тела узлов (`note`, `data`) не отдаются.
6. `depth` остаётся необязательным с умолчанием 2; потолки `MAX_TRAVERSAL_NODES = 200` и
   `MAX_TRAVERSAL_DEPTH = 3` не двигаются.
7. `graph::touch_node` при показе остаётся — **и остаётся ровно в одном месте**: в обработчике
   MCP `memory_recall` (`handlers/session.rs:266`). `access_count` инкрементирует только он. Ни
   общая функция ранга, ни `au recall --topic`, ни `au eval` `touch_node` не зовут, и это не
   стилистика: `au eval` открывает фикстуру только на чтение (`db::open_readonly`), а инкремент,
   спрятанный в общем пути recall, ронял бы каждый кейс отказом записи — прогон, а не кейс.
   Правило «только чтение» (FR-014a) написано про обработчик начала хода, не про recall;
   снимать инкремент в MCP спека не просит. Ценой этому — самоподкрепление сигнала `A`, поэтому
   его множитель в плане слабый и насыщаемый. Прочие инструменты трогают свои узлы своими
   вызовами (`handlers/task.rs:745`, `handlers/skill.rs:170,185`, `handlers/crud.rs:143`) — к
   пути recall это отношения не имеет и здесь не меняется.
8. Отказ — `Ok(json)`, не `Err`. `isError: true` остаётся признаком поломки, а не широкой темы.

**Снимок:**

9. `facts[].kind` — весь словарь значений, `facts[].text` — полный текст без обрезки,
   `facts[].at` — RFC 3339, тот же формат. `at` служит суррогатным идентификатором: ulika
   `latestSession()` (`ulika/hooks/lib/au.mjs:206-216`) отбирает `f.kind === 'session' && f.at`,
   нормализует наносекунды в миллисекунды регуляркой `/(\.\d{3})\d+/` и сравнивает **строки**.
   Смена формата времени сломает сопоставление «наш узел или чужой» молча.
10. `facts[].confidence` и `facts[].stale` — тоже без изменений. Полей у `Fact` **пять**, а не
    три: проверено чтением `graph/snapshot.rs:128-145`. Сторожит их не обзор, а `assert_eq!` по всей
    строке сериализации (`graph/snapshot.rs:581-594`), поэтому любое безусловно сериализуемое
    добавление — включая `"state":null` — красит тест сразу.
11. Порядок полей верхнего уровня: `project`, `facts`, затем `state`.
12. Пустой `facts` при коде 0 = «нечего сказать». Отсутствие вывода или ненулевой код = «сломан».
13. Заголовки `## N · Название`, формат `- строка` в теле, пропуск пустых секций, маркеры пустоты
    (`Хвостов нет — чисто.`), шапка `# Память Aurelius · … UTC`.
14. `memory_snapshot` отдаёт `{ "project", "markdown" }` и ничего больше.
15. Новых хуков на `SessionStart` и `Stop` не появляется (FR-002a), и блок состояния таких хуков
    не требует: он едет через `build_snapshot` (три markdown-формы) и через `snapshot_facts`
    (поле `state` машинной формы) — см. §3.2. Единственная правка `plugin/hooks.json` за всю
    фичу — `UserPromptSubmit` в фазе D, и она вне этого контракта. Одно условие к ней всё же
    записано здесь, потому что промах ловится не в этом файле, а в CI: **та же задача обязана
    поправить `crates/au/tests/plugin_manifest.rs:157`**, где список подкоманд захардкожен как
    `["db", "judge", "reindex", "skills", "touch", "trace"]` со словами «must be exactly …
    (six total)». Иначе `cargo test --workspace` краснеет на фазе D и остаётся красным до конца
    фичи.

**Что меняется намеренно и потому названо здесь:**

16. **`au pickup` в этом цикле порядок НЕ меняет.** `by_degree_then_recency` (`graph/mod.rs:157`)
    остаётся как есть и продолжает обслуживать два своих места (`pickup.rs:335,370`), где
    порядок по степени в подграфе — заявленное назначение команды. На `rank::score` переводится
    только путь recall: `handlers/session.rs` удаляет своё замыкание (`handlers/session.rs:253-259`) и сортирует
    `rank::score`. Третьей функции-компаратора не заводится — общей служит сам `rank::score`.
    Перевод `pickup` — отдельная задача **вне** этой фичи; до неё `au pickup` и `memory_recall`
    сознательно отвечают на разные вопросы разным порядком, и это записано здесь, чтобы
    расхождение читалось как решение, а не как забытый хвост.

## 5. Открытые вопросы

Ревизия закрыла четыре из шести. Закрытые оставлены с ответом, а не вычеркнуты: вычеркнутый
вопрос выглядит как незаданный, и его задают второй раз.

### Закрыты ревизией

- **OQ-2. Доставка блока «где остановились» — ЗАКРЫТ.** Блок виден во всех формах `au snapshot`,

  ней нет ни `--hook`, ни любого другого флага; строка `au snapshot --hook` в `plugin/hooks.json`
  рабочего дерева этой ветки **удалена** незакоммиченной правкой, тогда как установленный на
  машине плагин 3.4.4 её ещё несёт. Снимок ulika печатает вызовами
  `au snapshot --project <p>` (`ulika/hooks/lib/restore.mjs:185`) и `au snapshot --project <p> --json`
  (`ulika/hooks/lib/brief.mjs:191`), оба без `--hook`. Разбор — §3.2, «Где этот блок появляется».
- **OQ-4. Тест формы JSON — ЗАКРЫТ.** Выбран `skip_serializing_if`, тест
  `json_facts_shape_is_fixed_and_empty_means_nothing_to_say` (`graph/snapshot.rs:581-594`) не трогается
  и не ослабляется. Решение зафиксировано в §3.2 и в `data-model.md` §2.
- **OQ-5. `au pickup` наследует старый ранг — ЗАКРЫТ, но не так, как в прошлой редакции.**
  `au pickup` остаётся на `by_degree_then_recency` (`graph/mod.rs:157`) весь этот цикл: функцию

  вне этой фичи. См. §4 п. 16.
- **OQ-6. У `memory_recall` нет CLI-двойника — ЗАКРЫТ.** `au recall` получает флаг `--topic`.
  Проверено: команда существует (`crates/au/src/commands.rs:825`, `RecallArgs` —
  `commands.rs:806-817`) и умеет два входа — точный UUID/`subject` и `--prefix` (фасет,
  `commands.rs:961`), взаимоисключимые через `conflicts_with`/`required_unless_present`. Значит

  идёт тем же путём, что `memory_recall`, и печатает ту же прозу через `render.rs`. Существует он
  затем, чтобы SC-001 («тема «au» получает отказ, а не 162 записи») проверялась командой, а не
  глазами. Устройство флага — `contracts/cli.md`; задача на него принадлежит фазе B.
