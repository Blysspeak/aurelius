# Feature Specification: Граф внешней документации как источник

**Feature Branch**: `008-doc-graph`
**Created**: 2026-09-04
**Status**: Draft
**Input**: задача `047fa182` (проект aurelius). Выкачать документацию стороннего сервиса (первый
случай — API Банка 131, 166 страниц × 2 локали), положить её в память как граф с направленными
упорядоченными рёбрами и уметь отвечать на вопрос «какие шаги ведут к X» лесенкой, а не окрестностью.

## Почему это вообще заводится

Сегодня граф доки можно залить только поштучно: `memory_add` на узел и `memory_relate` на ребро,
каждый вызов через линтер и пробу. Для сотен страниц и рёбер это тысячи вызовов — заливка съедает
сессию. Залитое попадает в общий снапшот и раздувает `memory_status`. А главный вопрос — «что нужно
знать до `payment_finished`» — `memory_context` не отвечает: он отдаёт соседей, лесенку из них не
собрать.

Приоритет владельца: пункты 1 (bulk-импорт), 4 (лесенка), 6 (слой вне снапшота). Без них заливка
либо съест сессию, либо засорит снапшот, а вопрос о шагах останется ручным.

## Clarifications

### Session 2026-09-04

- Q: Кто выкачивает сайт? → A: внешний скрипт, отдающий `graph.json`. `au` только импортирует.
  Crawl внутри `au` (п. 2 задачи) — отдельная фича, эту волну от HTTP не зависим.
- Q: Чем узел страницы привязан к проекту и источнику? → A: полем `data.source_id` и
  `data.project`, без рёбер. Ребро к хабу воспроизвело бы хаб-взрыв обхода на глубину 2.
- Q: Где хранить номер шага у `next_step`? → A: в `weight` ребра. Колонка `data` у edges —
  миграция схемы, тир money-full, отклонено.
- Q: Идентичность узла при повторном импорте? → A: `data.subject` (индекс `idx_nodes_subject`).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Заливка графа одной командой (Priority: P1)

Скрипт выкачал доку и собрал `graph.json`: узлы с `subject`, тела в двух локалях, рёбра по
`subject`. Человек делает `au graph import graph.json`. Всё ложится одной транзакцией. Повторный
прогон того же файла ничего не дублирует; прогон изменённого файла трогает только изменившееся.

**Independent Test**: импорт файла на 3 узла и 2 ребра; второй импорт того же файла — 0 создано,
0 обновлено; импорт с изменённым телом одного узла — 1 обновлено, рёбра не задвоены.

**Acceptance Scenarios**:

1. **Given** файл с N узлами и M рёбрами, **When** `au graph import`, **Then** в графе ровно N
   новых узлов и M рёбер, отчёт называет числа создано/обновлено/без изменений.
2. **Given** тот же файл, **When** импорт повторён, **Then** создано 0, обновлено 0, рёбра не
   задвоены.
3. **Given** файл, где ребро ссылается на неизвестный `subject`, **When** импорт, **Then** ни одна
   запись не сохраняется, ошибка называет ребро и `subject`.
4. **Given** файл на 400 узлов и 600 рёбер, **When** импорт, **Then** он завершается за секунды,
   а не за сессию (SC-001).

### User Story 2 — Лесенка шагов, а не окрестность (Priority: P1)

Человек спрашивает: «какие шаги от `session/create` до `payment_finished`» или «что нужно знать до
`payment_finished`». Система отдаёт упорядоченную цепочку по направленным рёбрам, а не мешок
соседей.

**Independent Test**: граф A →next_step(1)→ B →next_step(2)→ C, D →prerequisite→ C.
`au path A C` даёт A, B, C в этом порядке. `au path --before C` даёт D и B (и A) как условия.

**Acceptance Scenarios**:

1. **Given** цепочка `next_step` от A до C, **When** `au path A C`, **Then** вывод — узлы по
   порядку шагов, каждый с номером шага и подписью.
2. **Given** к C ведут `prerequisite` от D и `next_step` от B, **When** `au path --before C`,
   **Then** вывод перечисляет D и B (и предшественников B) в порядке «сначала то, что раньше».
3. **Given** пути нет, **When** `au path A Z`, **Then** внятное «пути нет», код возврата 1, без
   вывода соседей.
4. **Given** тот же вопрос через MCP, **When** `memory_path`, **Then** тот же ответ в JSON.

### User Story 3 — Дока не раздувает снапшот (Priority: P1)

После заливки 332 страниц `memory_status` показывает то же, что до неё: задачи, решения, сессии.
Страницы находятся через `au search` и `au context`, но не занимают слои 1–6 снапшота.

**Independent Test**: залить тестовый граф из 50 узлов типа `doc`; снапшот до и после
совпадает по слоям 1–6; `au search` находит страницу по слову из тела.

**Acceptance Scenarios**:

1. **Given** залитый слой `vendor-docs`, **When** `memory_status`, **Then** ни одна страница
   не входит в слои 1–6.
2. **Given** тот же слой, **When** `au search <слово из тела>`, **Then** страница находится.

### User Story 4 — Подграф в картинку (Priority: P3)

`au graph export --format mermaid --source-id bank131-docs` печатает подграф источника
в mermaid: узлы подписаны `label`, рёбра — отношением и шагом.

### Edge Cases

- Узел без `subject` в файле — отказ до записи, с номером узла.
- Два узла с одним `subject` в одном файле — отказ, не «последний победил».
- `next_step` без `step` — принимается как шаг 1; два `next_step` из одного узла с одним шагом —
  принимаются (ветвление), порядок между ними по `label`.
- Цикл в `prerequisite` — `--before` завершается, каждый узел печатается один раз, цикл
  помечается предупреждением.
- Импорт в проект, которого нет в графе — отказ, а не молчаливое создание проекта.

## Requirements *(mandatory)*

### Functional Requirements

**Импорт**

- **FR-001**: `au graph import <file>` ДОЛЖЕН принимать JSON вида `{source, nodes[], edges[]}`
  (см. Key Entities) и писать узлы и рёбра одной транзакцией: либо всё, либо ничего.
- **FR-002**: Узел ДОЛЖЕН отождествляться по `data.subject`: существующий с тем же `subject`
  обновляется, отсутствующий создаётся. Неизменившийся (по `content_hash`) не переписывается.
- **FR-003**: Ребро ДОЛЖНО отождествляться тройкой (from, to, relation); повторный импорт не
  создаёт второго такого ребра. Для `next_step` `weight` ДОЛЖЕН равняться номеру шага.
- **FR-004**: Отчёт импорта ДОЛЖЕН называть: узлов создано/обновлено/без изменений, рёбер
  создано/уже были, длительность. Флаг `--json` даёт то же машинно.
- **FR-005**: Рёбра ссылаются на узлы по `subject`; ссылка на неизвестный `subject` — отказ
  всей транзакции с именем ребра.
- **FR-006**: Узел страницы НЕ ДОЛЖЕН получать рёбер к узлу проекта или узлу источника.
  Принадлежность — поля `data.project` и `data.source_id`.

**Словарь рёбер**

- **FR-007**: В `Relation` ДОЛЖНЫ появиться `prerequisite`, `next_step`, `defines`,
  `references` — направленные, разбираемые `parse_known` и доступные `au relate`
  и `memory_relate`.

**Лесенка**

- **FR-008**: `au path <from> <to>` ДОЛЖЕН находить кратчайший направленный путь по рёбрам
  `next_step` и `prerequisite` и печатать узлы по порядку с номером шага.
- **FR-009**: `au path --before <X>` ДОЛЖЕН отдавать все узлы, от которых к X ведут
  `prerequisite`/`next_step` транзитивно, в топологическом порядке; цикл не зацикливает.
- **FR-010**: `from`, `to`, `X` разрешаются: UUID → точный `subject` → точный `label`;
  неоднозначность — отказ с перечнем кандидатов, не «первый попавшийся».
- **FR-011**: Тот же ответ ДОЛЖЕН быть доступен через MCP как `memory_path` с полями
  `from`, `to` | `before`, `max_depth`.

**Слой вне снапшота**

- **FR-012**: Узлы страниц ДОЛЖНЫ иметь `node_type = doc` и `data.layer = "vendor-docs"`.
- **FR-013**: Слои 1–6 снапшота (`gather`) НЕ ДОЛЖНЫ включать узлы типа `doc`; тест это
  закрепляет.
- **FR-014**: `au search`, `au context`, `memory_search`, `memory_context` ДОЛЖНЫ находить
  узлы `doc` наравне с остальными.

**Экспорт**

- **FR-015**: `au graph export --format mermaid [--source-id <id>]` ДОЛЖЕН печатать подграф в
  синтаксисе mermaid `graph LR`; без `--source-id` — весь граф.

### Key Entities

- **graph.json**:
  ```json
  {
    "source": {"id": "bank131-docs", "project": "xhub", "url": "https://docs.bank131.ru", "fetched_at": "2026-09-04T10:00:00Z"},
    "nodes": [
      {"subject": "https://docs.bank131.ru/api/methods#sessioncreate",
       "label": "session/create", "type": "doc",
       "bodies": {"en": "...markdown...", "ru": "...markdown..."},
       "locale_default": "en",
       "data": {"url": "...", "anchor": "sessioncreate", "sha256": {"en": "...", "ru": "..."}}}
    ],
    "edges": [
      {"from": "<subject>", "to": "<subject>", "relation": "next_step", "step": 2}
    ]
  }
  ```
- **Узел `doc`**: `label` — короткое имя метода/раздела; `note` — тело локали по умолчанию
  (в FTS); `data.bodies` — все локали; `data.subject` — URL с якорем; `data.layer`,
  `data.source_id`, `data.project`, `data.url`, `data.anchor`, `data.sha256`,
  `data.fetched_at`. Один узел на якорь, не на страницу; en/ru — один узел, два тела.
- **Ребро шага**: `relation = next_step`, `weight = step`. `prerequisite` — «нужно знать до».
  `defines` — раздел определяет термин/сущность. `references` — упоминает.

## Success Criteria *(mandatory)*

- **SC-001**: Импорт 400 узлов и 600 рёбер укладывается в 10 секунд на ноутбуке владельца.
- **SC-002**: Повторный импорт неизменённого файла — 0 записей в `nodes`/`edges`.
- **SC-003**: Вопрос «что до `payment_finished`» отвечается одной командой упорядоченным списком.
- **SC-004**: Размер `memory_status` до и после заливки 332 страниц отличается не более чем
  строкой счётчика архива.
- **SC-005**: `cargo fmt`, `cargo clippy -D warnings`, `cargo test --workspace` зелёные.

## Assumptions

- Скрипт-выкачка живёт в проекте потребителя (xhub) и отвечает за HTML→Markdown, sha256 и
  сбор рёбер. `au` доверяет файлу.
- Схема БД не меняется: ни новых таблиц, ни колонок. Новые варианты `Relation` и `NodeType`
  — код, не миграция.

## Out of Scope

- `au doc crawl` (п. 2), `verify_with` по живому URL (п. 7), кросс-ссылка код↔дока (п. 8) —
  следующие волны той же задачи `047fa182`.
