# Feature Specification: Гибридный поиск и Dense Retrieval

**Feature Branch**: `011-dense-retrieval`
**Created**: 2026-09-13
**Status**: Ready
**Input**: Кросс-язычный поиск мёртв: 24/30 русских запросов к английским документам = 0 результатов. Нужно добавить dense retrieval через эмбеддинги (BGE-M3), гибридный поиск через RRF и опциональный reranker, не ломая существующий FTS5.

## Почему это вообще заводится

Текущее состояние: retrieval только через FTS5 BM25 → seed-узлы → BFS по графу → ранг по P·R·A·T. Заметки (100-500 токенов) — смесь RU, EN и кода.
Стемминг (спека 010) решает проблему морфологии, но кросс-язычный барьер (RU запрос → EN документ) и поиск по смыслу FTS5 не берёт концептуально.

Что делает эта спека:
1. Добавляет векторный поиск через embedding-модель BGE-M3 и sqlite-vec.
2. Объединяет выдачи FTS5 и KNN через Reciprocal Rank Fusion (RRF).
3. Добавляет контекст к заметкам перед векторизацией (Contextual Prepending).
4. Подключает опциональный reranker (Qwen3-Reranker-0.6B) для топ-30 кандидатов после графа.

Чего спека НЕ делает:
- Q4 квантование на эмбеддингах ЗАПРЕЩЕНО (потеря 4-8% NDCG). Только FP16/FP32 для инференса, int8 для хранения.
- Не трогает существующий путь FTS5 (`nodes_fts`, `nodes_stem_fts`).
- Не трогает формат `au snapshot --json` (контракт ulika).
- Сама модель в git не включается, только путь в переменной окружения `AURELIUS_MODELS_DIR` (единого механизма конфигурации в проекте нет — см. Clarifications).
- Не падает и не деградирует молча, если демон (единственный владелец модели, см. Clarifications) недоступен: гибридный поиск в таком случае обязан откатиться на полнотекстовую FTS5-выдачу и явно пометить откат в выводе (человеческом и `--json`) — тихий откат снаружи неотличим от поиска, который просто стал глупее без причины.

## Clarifications

- Q: Как хранить векторы? → A: sqlite-vec (int8). Чистый C, статическая линковка, SIMD. Сжатие 4x (vec_quantize_int8), потеря <1%. 100k заметок × 1024 dim × int8 = ~100 MB.
- Q: Какой Runtime для инференса? → A: fastembed-rs (под капотом ort, поддержка CUDA).
- Q: Архитектура пайплайна? → A: Query → [FTS5 BM25 top-50] + [dense KNN top-50] → RRF (k=60) → top-12 seeds → Graph 2-hop → ~20-30 candidates → Reranker → top-5.
- Q: Как ранжируем сиды? → A: `r` в формуле P·R·A·T = нормализованный RRF-скор сида, вместо фиксированного `r_traversed`.
- Q: Если fastembed-rs не поддерживает BGE-M3? → A: План Б — `ort` + ручная обвязка.
- Q: Меры MRR (средняя обратная позиция первого правильного ответа) нет в `eval.rs` — на что опирается гейт «рост MRR» (тесты T017, US2)? → A: Добавляется новый вид кейса `crosslingual_top5` (русский запрос обязан найти англоязычную заметку в первой пятёрке — см. `data-model.md`) и поле `mrr` в отчёте `au eval`, считается по кейсам видов `recall_top5` и `crosslingual_top5`: позиция 1 → вклад 1, позиция 2 → 1/2, …, позиция 10 → 1/10, не найден → 0, среднее по кейсам. Отвергнута новая отдельная команда — расширение существующего `au eval` дешевле и не плодит второй источник истины. Фикстура (`.db`) закреплена по sha256 (`contracts/eval-cases.md` §1.1). Валидный кейс `crosslingual_top5` требует, чтобы в замороженной фикстуре нашлась пара «RU-тема → EN-узел», и если её для этого нужно доснять — новая фикстура даёт новый `fixture_sha256`, который прописывается в `meta.fixture_sha256` отдельным шагом, иначе `au eval` падает на сверке (`eval.rs::verify_fixture`, код 14). Сам файл `cases.jsonl` в сверку sha256 не входит (сверяется только `.db`) — но это не мешает шагу быть обязательным, если фикстура пересъёмывается.
- Q: Какая точка отсчёта у «роста recall vs baseline»? → A: Числа нет и не выдумывается: перед фазой C обязателен отдельный замер `au eval --json` на текущем FTS5 (без векторов) — его результат и есть точка отсчёта. Замер от 26.07.2026 (24/30 кросс-язычных запросов дали 0 результатов, recall@1 5/30, recall@10 6/30) сделан на другой системе (node:sqlite FTS5) и для aurelius не показатель, годится только как ориентир. Гейт: строго больше точки отсчёта по recall на кросс-язычных кейсах, без ухудшения на существующих одноязычных кейсах. Конкретное целевое число назначается после замера, а не заранее — сознательное решение, а не недосмотр.
- Q: Пути к весам модели нет в конфиге, потому что конфига в проекте нет вообще — как задавать путь? → A: Переменная окружения `AURELIUS_MODELS_DIR`, по умолчанию `$AURELIUS_HOME/models`; ложится в существующее соглашение из восьми переменных `AURELIUS_*`. Отвергнут отдельный файл конфига: механизма конфигурации в проекте нет, заводить его ради одного пути несоразмерно. Хардкод `/home/blyss/.local/share/aurelius/models/` в `crates/aurelius-core/src/embed.rs:7` подлежит замене; отсутствие весов по пути — внятный отказ с указанием ожидаемого пути, а не паника.
- Q: Фаза D («online embedding при записи») требует синхронного расчёта эмбеддинга в `memory_add`/`add_node_full` (~15 мс на GPU) — это противоречит задаче трекера `f7649880`, которая требует незаблокированной записи (<10 мс) с фоновой досчёткой пачками. Как разрешить? → A: Запись узла кладёт его id в таблицу-очередь `embedding_queue` и возвращается немедленно; модель при записи `au note` не грузится. Демон (тот же процесс, что уже владеет часами напоминаний) держит BGE-M3 в памяти постоянно и разбирает очередь пачками на своих тактах. Довод: `au` — короткоживущий процесс, на каждый вызов пришлось бы грузить 2.2 ГБ весов заново — это секунды, а не 15 мс; цифра 15 мс верна только для процесса, который держит модель в памяти постоянно, то есть для демона. Отвергнута синхронная схема исходного плана — противоречит `f7649880`. Риск: свежая заметка становится видна векторному поиску не мгновенно, а к ближайшему такту демона — это закрывает противоречие с `f7649880`, но требует переформулировки гейта T014 через такт демона, а не через «сразу».
- Q: Демон, разбирающий очередь эмбеддингов, — на видеокарте или на CPU? → A: Демон пробует видеокарту при старте, при неудаче откатывается на CPU; решение принимается один раз при старте и пишет в журнал, какой путь выбран. Риск: BGE-M3 просит ~1.2 ГБ видеопамяти, реранкер (фаза E) ещё ~1.3 ГБ, вместе 2.5 ГБ на карте в 8 ГБ, которую делят с другими моделями.
- Q: Фаза D закрыла загрузку модели на запись очередью — а кто векторизует сам поисковый запрос на чтении (`au recall`)? Векторизовать надо обе стороны: и заметку при записи, и запрос при поиске; перенос записи в очередь не убрал проблему холодной загрузки 2.2 ГБ весов, а переместил её с записи на чтение — `au recall` тоже короткоживущий процесс. → A: Решение владельца 16.09.2026, дословно «пусть демон несёт»: демон (`Commands::Daemon`, `crates/au/src/main.rs:721`; реализация `crates/au/src/commands.rs:3072`) — единственный владелец модели во всей системе, и для записи, и для чтения. Он грузит BGE-M3 один раз при старте и держит постоянно; CLI и MCP-сервер весов не грузят вообще — тонкие клиенты, шлют текст запроса демону по сокету `$AURELIUS_HOME/embed.sock` и получают обратно вектор размерности 1024 (не результаты поиска — KNN по `node_embeddings` клиент делает сам, он и так открывает базу). Протокол — `data-model.md` §6. Отвергнута альтернатива: каждый долгоживущий процесс грузит свою копию модели — их минимум три (демон, MCP-сервер, сервер синхронизации), по 1.2 ГБ видеопамяти каждая, вместе с реранкером (ещё 1.3 ГБ) упирается в карту 8 ГБ, которую делит Ollama. Цена: демон становится несущим для поиска, а не только владельцем часов напоминаний — расширение его роли за пределы того, ради чего он заводился.
- Q: Что если демон недоступен или не запущен в момент `au recall`? → A: Обязательное условие, без которого решение «пусть демон несёт» вредно: поиск НЕ падает, а осознанно откатывается на полнотекстовую FTS5-выдачу и ЯВНО сообщает об этом в выводе (человеческом и `--json`). Без такой пометки откат снаружи неотличим от того, что поиск просто стал глупее без причины — молчаливая деградация хуже явной.

## Отвергнутые альтернативы

- **jina-v3**: CC-BY-NC-4.0 лицензия (не подходит).
- **deepvk/USER-bge-m3**: языковой дрейф на кросс-язычном.
- **FRIDA**: контекст всего 512 токенов.
- **ColBERT**: 20-50x оверхед хранения, бессмыслен для 30 коротких заметок.
- **sqlite-vss**: заброшен, тянет Faiss зависимость.
- **nomic-embed-text-v1.5**: слаб на кириллице.

## User Scenarios & Testing

### User Story 1 — Кросс-язычный поиск (Priority: P1)
Человек ищет по-русски, находит английскую заметку по смыслу.
**Independent Test**: `au recall` на RU запросе отдаёт релевантную EN заметку. До фазы C снят точечный замер `au eval --json` на текущем FTS5 — это точка отсчёта; `au eval` после фазы C показывает рост recall по кейсам `crosslingual_top5` строго выше этой точки отсчёта, без ухудшения на существующих `recall_top5`/`morphology`.

### User Story 2 — Точность выдачи через Reranker (Priority: P2)
После графа кандидаты пересортировываются реранкером.
**Independent Test**: `au eval` показывает рост поля `mrr` (среднее по кейсам `recall_top5` и `crosslingual_top5`, см. `data-model.md`) vs волна C (только RRF).
