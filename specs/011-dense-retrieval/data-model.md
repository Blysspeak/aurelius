# Data Model: Гибридный поиск и Dense Retrieval

**Feature**: `011-dense-retrieval` | **Date**: 2026-09-13

## 1. Таблица `node_embeddings` (sqlite-vec)
Таблица для хранения int8 векторов размерности 1024.
DDL (миграция v15→v16):
```sql
CREATE VIRTUAL TABLE node_embeddings USING vec0(
    rowid INTEGER PRIMARY KEY,
    embedding INT8[1024]
);
```
Хранение: ~100 MB на 100k заметок. Сжатие: `vec_quantize_int8(embedding, 'unit')`.

## 1a. Таблица `embedding_queue` (миграция v16→v17)

Очередь фазы D: запись узла (`memory_add` / `add_node_full`) кладёт сюда `node_id` и возвращается немедленно, не дожидаясь эмбеддинга и не загружая модель. Разбирает очередь пачками `au daemon` на каждом такте (`daemon_tick`, `crates/au/src/commands.rs:3036`) — модель у него уже в памяти.

DDL (миграция v16→v17):
```sql
CREATE TABLE embedding_queue (
    node_id    TEXT PRIMARY KEY REFERENCES nodes(id),
    queued_at  TEXT NOT NULL,
    attempts   INTEGER NOT NULL DEFAULT 0
);
```

Поля:
- `node_id` — идентификатор узла, ждущего эмбеддинга. `PRIMARY KEY`, не отдельный автоинкремент: повторная запись того же узла (правка заметки до того, как демон успел её обработать) обязана лечь на ту же строку, а не породить дубль в очереди — `INSERT OR REPLACE` обновляет `queued_at`, не плодя вторую попытку эмбеддинга того же узла.
- `queued_at` — момент постановки в очередь (RFC 3339). Нужен для порядка обработки (FIFO по возрастанию) и для диагностики, если очередь растёт быстрее, чем демон её разбирает.
- `attempts` — число неудачных попыток эмбеддинга этого узла. Инкрементируется при ошибке инференса (например, модель не поднялась), не при успехе. Строка удаляется из `embedding_queue` сразу после успешной записи в `node_embeddings` — так что живые строки таблицы это ровно то, что ещё предстоит обработать.

Падение демона на середине пачки: демон удаляет строку из `embedding_queue` только ПОСЛЕ успешной записи соответствующего вектора в `node_embeddings`, в одной транзакции на узел (или на пачку). Если процесс демона падает между записью части пачки и удалением остальных строк, уже обработанные узлы не переобрабатываются (их строк в очереди больше нет), а необработанные остаются в очереди и подхватываются следующим тактом после перезапуска демона — потерь и дублей эмбеддингов на этом стыке нет. Узел, у которого `attempts` растёт без остановки (модель стабильно падает на его тексте), не блокирует остальную очередь: демон продолжает разбирать остальные строки, а не останавливается на первой ошибке.

## 2. RRF (Reciprocal Rank Fusion) Формула
Слияние результатов FTS5 и Dense KNN:
```rust
RRF_Score = 1.0 / (k + rank_fts5) + 1.0 / (k + rank_dense)
```
Константа `k` = 60. `r` в итоговой формуле P·R·A·T = нормализованный RRF_Score.

## 3. Contextual Prepending Формат
Перед векторизацией к тексту заметки дописывается метаданный заголовок:
```text
[Project: {project} | Type: {node_type} | Subject: {subject} | {created_at}]
{text}
```
Пример:
```text
[Project: aurelius | Type: decision | Subject: storage | 2026-09-13]
<текст заметки>
```
Это даёт BGE-M3 точные структурные подсказки для поиска без необходимости хранить отдельные колонки-фильтры в векторе.

## 4. Новый вид кейса оценки `crosslingual_top5`

Расширение контракта `specs/010-waking-memory/contracts/eval-cases.md` (§1.3, §2.1) шестым видом. Формат `input`/`expect` — буквально тот же, что у `recall_top5` (§2.1 контракта), и судится тем же правилом «нужный узел в топ-5»; отличие только в семантике самого кейса — запрос и ожидаемый узел обязаны быть на разных языках (в первую очередь RU-запрос → EN-заметка, ради чего и заводится вся спека 011):

```
input:  { "topic": строка, "project": строка?, "depth": целое? }
expect: { "top5": [UUID, …], "mode": "any"|"all"?, "forbid_types": [строка]? }
```

Поля, судейство (`PASS`/`FAIL`/`SKIP`, позиции, `forbid_types`, ничьи) и общие требования §2 (секреты, `why`, `tags` с обязательной меткой `by:`) — идентичны `recall_top5`. `kind: "crosslingual_top5"` в строке кейса — единственное отличие формата. `why` обязан называть язык запроса и язык заметки явно (например: «владелец, …: RU-запрос, EN-заметка, узел признан единственным верным ответом»), чтобы отчёт о провале не заставлял перечитывать фикстуру для проверки, что кейс вообще кросс-язычный.

`fixture_sha256` в `meta` (контракт §1.1) закреплён по фикстуре БД (`.db`), а не по файлу `cases.jsonl` — сверки самого файла кейсов на sha нет. Но валидный кейс `crosslingual_top5` требует, чтобы в замороженной фикстуре гарантированно нашлась пара «RU-тема → EN-узел»; если ради этого фикстуру приходится доснять заново, новый `.db` даёт новый `fixture_sha256`, и его нужно явно прописать в `meta.fixture_sha256` — иначе `au eval` откажет на `eval::verify_fixture` (`crates/aurelius-core/src/eval.rs`, ошибка `FixtureChanged`, код 14). Это отдельный шаг (T020 в `tasks.md`), а не побочный эффект добавления строк в JSONL.

Полы по количеству кейсов (контракт §1.5) для `crosslingual_top5` не назначаются в этом документе — они назначаются вместе с самой фикстурой (T020) и точкой отсчёта (T022) и не выдумываются здесь без замера.

## 5. Мера `mrr` в отчёте `au eval`

`mrr` (mean reciprocal rank, средняя обратная позиция) — новое поле отчёта `au eval` (человеческий вывод и `--json`), закрывающее гейт «рост MRR» (`tasks.md` T017, `spec.md` US2). Считается по кейсам видов `recall_top5` и `crosslingual_top5`; кейсы остальных трёх видов в `mrr` не участвуют, как в них не участвует и текущий recall.

Для одного кейса `c` из этих двух видов:
```
rr(c) = 1 / position(c)   если ожидаемый узел найден на позиции position(c) в выдаче (1-индексация)
rr(c) = 0                  если ни один ожидаемый узел не найден
```
При нескольких UUID в `expect.top5` (`mode: "any"`, умолчание) берётся позиция первого из них, встреченного в выдаче — то есть та же позиция, которую отчёт уже печатает в разборе провала (`positions_report`, `crates/aurelius-core/src/eval.rs`). `SKIP`-кейсы (узел вырезан обезличиванием и т. п.) в сумму и в счётчик `mrr` не входят — тем же правилом, что и в доле по видам (контракт §2, §5 п.3): пропуск не должен искажать среднее.

Итоговое значение:
```
mrr = (Σ rr(c) по всем пригодным кейсам recall_top5 и crosslingual_top5) / (число этих пригодных кейсов)
```
Если пригодных кейсов обоих видов нет вовсе — `mrr` не печатается как число (то же состояние «нет кейсов», что и в долях по видам, контракт §5 п.3), а не 0: ноль был бы неотличим от «все промахнулись».

## 6. Протокол обмена по сокету `$AURELIUS_HOME/embed.sock` (векторизация запроса на чтении)

Демон — единственный держатель весов BGE-M3 и для записи (`embedding_queue`, §1a), и для чтения: `au recall` и MCP-поиск не грузят модель, а посылают текст запроса демону и получают обратно готовый вектор. KNN-поиск по `node_embeddings` при этом делает сам клиент на своём соединении с базой — демон результатов поиска не считает и с базой в этом обмене не работает.

Готового механизма межпроцессного обмена в проекте нет, переиспользовать нечего: демон и MCP-сервер сегодня вообще не общаются друг с другом напрямую, а синхронизируются только через общую SQLite (пример: `crates/aurelius/src/mcp/handlers/reminder.rs` работает с `reminders::*` прямо на своём `Connection`, не обращаясь к демону). Поиск `UnixListener`/`UnixStream`/`.sock`/`ipc` по всему `crates/` — 0 совпадений (проверено 16.09.2026). Значит unix-сокет для эмбеддингов — новый механизм в проекте, а не переиспользование существующего.

Путь: `$AURELIUS_HOME/embed.sock` — та же директория, где уже лежат база и замок демона `aurelius-remind.lock` (`daemon_lock_path`, `crates/au/src/commands.rs:2927`), тем же принципом (каталог по `db_path()`/активному дому, не отдельный жёстко заданный путь). Отдельная зависимость не нужна: корневой `Cargo.toml:22` уже подключает `tokio` с фичей `full`, куда входит `tokio::net::UnixListener`/`UnixStream`.

Обмен — один запрос, один ответ, без долгоживущего соединения:
- Клиент → демон: `{"query": "<текст запроса>"}`. Без Contextual Prepending (§3) — тот формат для заметок при записи, к поисковому запросу неприменим.
- Демон → клиент при успехе: `{"vector": [1024 значения f32]}` (та же модель и тот же путь инференса, что и на запись, `crates/aurelius-core/src/embed.rs`).
- Демон → клиент при ошибке инференса (пустой текст, модель упала и т.п.): `{"error": "<причина>"}`, соединение закрывается без вектора.
- Сокета нет вообще (демон не запущен) или соединение не устанавливается: клиент не ждёт и не ретраит — это тот же случай, что и `{"error": ...}`. В обоих случаях клиент откатывается на полнотекстовый FTS5-поиск и обязан явно пометить это в выводе (человеческом и `--json`) — правило и его обоснование в `spec.md` (Clarifications) и `plan.md` (Важные ограничения, п.5).
