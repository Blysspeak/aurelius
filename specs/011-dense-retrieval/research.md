## Выбор Embedding-модели

### BAAI/bge-m3 (567M) - ПРИНЯТО
- **Характеристики**: rusBEIR 0.5008, кросс-язычный SOTA в классе ≤600M. Dense + sparse гибрид, 8192 контекст, 1024 dim.
- **Вес**: ONNX FP32 2.2 GB. Путь задаётся переменной окружения `AURELIUS_MODELS_DIR`, по умолчанию `$AURELIUS_HOME/models` (сегодня захардкожен в `crates/aurelius-core/src/embed.rs:7` как `/home/blyss/.local/share/aurelius/models/` — подлежит замене, единого механизма конфигурации в проекте нет, см. ниже). Отсутствие весов по пути — внятный отказ с ожидаемым путём, не паника.
- **VRAM**: ~1.2 GB (FP16 инференс).
- **Латентность инференса**: 15мс на GPU — верно только для процесса, который держит модель в памяти постоянно (см. «Где живёт модель» ниже), а не для короткоживущего `au`.

### Отвергнутые модели
- **deepvk/USER-bge-m3**: языковой дрейф на кросс-язычном.
- **FRIDA**: малый контекст (512).
- **ColBERT**: 20-50x оверхед хранения, не оправдан для 30 коротких заметок.
- **nomic-embed-text-v1.5**: слаб на кириллице.

## Runtime и Хранение

### Runtime: fastembed-rs (крейт `fastembed`)
- Production-ready (используется Qdrant), embedding + reranker из коробки.
- Под капотом `ort` (ONNX Runtime) с поддержкой CUDA.

### Хранение: sqlite-vec
- **Отвергнуто**: `sqlite-vss` (заброшен, Faiss зависимость).
- **Принято**: `sqlite-vec` (int8). Чистый C, статическая линковка, SIMD.
- **Размер**: `vec_quantize_int8(embedding, 'unit')` даёт сжатие 4x (потеря <1%). 100k заметок = ~100 MB.

## Где живёт модель — процесс демона, а не `au`

### Проблема
`au` — короткоживущий процесс командной строки: каждый вызов `au note` — новый процесс. Загрузка BGE-M3 (2.2 GB ONNX FP32) на каждый вызов стоит секунды, а не заявленные 15 мс — цифра 15 мс измерена для модели, уже находящейся в памяти, и переносить её на холодный старт CLI некорректно. Это же прямо противоречит задаче трекера `f7649880`, требующей записи узла быстрее 10 мс.

### Принято
Модель BGE-M3 грузится и держится в памяти постоянно процессом `au daemon` (`crates/au/src/commands.rs:3072` — уже существующий долгоживущий процесс с файловым локом против второго экземпляра, `commands.rs:2966`, и циклом тактов `daemon_tick`, `commands.rs:3036`). Запись узла (`memory_add` / `add_node_full`) кладёт id узла в таблицу-очередь `embedding_queue` (см. `data-model.md`) и не грузит модель. На каждом такте демон разбирает очередь пачками, используя уже загруженную модель — отсюда и достижимость цифры ~15 мс на эмбеддинг.

### Отвергнуто
Синхронный расчёт эмбеддинга внутри `memory_add` (исходная редакция плана, фаза D) — верен по латентности только для процесса, который не перезапускается на каждый вызов. Для `au` это означало бы линейный рост времени `au note` на секунды хоть на GPU, хоть на CPU, и напрямую нарушает `f7649880`.

### Риск
Свежая заметка получает вектор не мгновенно, а к ближайшему такту демона — задержка видимости для векторного поиска порядка интервала такта. Гейт фазы D (T014) формулируется через «после такта демона», а не через «сразу после записи».

### Чтение: то же самое, только запрос вместо заметки
Перенос записи в очередь (`embedding_queue`) не убирает проблему холодной загрузки весов — он переносит её с записи на чтение. `au recall` тоже короткоживущий процесс: без демона векторизация запроса означала бы те же секунды на загрузку 2.2 ГБ на каждый поиск, что и на запись до фазы D. Решение владельца 16.09.2026, дословно «пусть демон несёт»: демон — единственный владелец модели во всей системе, для записи и для чтения одинаково. Он поднимает unix-сокет `$AURELIUS_HOME/embed.sock`, векторизует по нему текст запроса и отдаёт клиенту готовый вектор 1024d; сам KNN-поиск по `node_embeddings` клиент выполняет своим соединением с базой — демон в нём не участвует. CLI и MCP-сервер весов не грузят вообще. Протокол — `data-model.md` §6.

Готового IPC демон↔клиенты в проекте не было: сегодня демон и MCP-сервер синхронизируются только через общую SQLite (пример — доставка напоминаний, `crates/aurelius-core/src/reminders.rs`, `crates/aurelius/src/mcp/handlers/reminder.rs`), прямого обмена сообщениями между процессами нет нигде (`grep -rn "UnixListener\|UnixStream\|\.sock" crates/` — 0 совпадений на 16.09.2026). Сокет для эмбеддингов — новый механизм, а не переиспользование существующего.

Отвергнуто: каждый долгоживущий процесс грузит свою копию модели — их минимум три (демон, MCP-сервер, сервер синхронизации), по ~1.2 ГБ VRAM каждая; вместе с реранкером фазы E (~1.3 ГБ) это не помещается в карту 8 ГБ, которую делит Ollama.

Обязательное условие: демон недоступен или сокет не отвечает → поиск не падает, а осознанно откатывается на FTS5-only выдачу и явно сообщает об этом в выводе — без такой пометки откат неотличим от того, что поиск просто стал глупее без причины. Цена решения: демон становится несущим для поиска, а не только владельцем часов напоминаний — расширение его роли за пределы того, ради чего он заводился.

### Устройство инференса — GPU или CPU
Не было решено ни в одной прежней редакции. Принято: демон при старте пробует GPU, при неудаче откатывается на CPU; выбор делается один раз за запуск процесса и логируется. Риск: BGE-M3 просит ~1.2 GB VRAM, реранкер (фаза E) — ещё ~1.3 GB, вместе 2.5 GB на карте в 8 GB, разделяемой с другими моделями.

## Точка отсчёта — замерена 16.09.2026, до фазы C

Требование T022: замер обязан быть сделан **до** того, как фаза C подменит `r` в формуле ранга, иначе сравнивать рост не с чем.

```
au eval --json, фикстура aurelius-2026-09-08.db
fixture_sha256  dc217a63e7fcb3f2fae0b91885a3b1936b675006064dac3efb2517c3305d688b
digest          580f41b159bf373f

кейсов 65     пройдено 28, провалено 37
recall_top5   24/41   58,5 %
morphology     4/24   16,7 %
```

Прогон воспроизводим: `digest` обязан совпасть при повторе на той же фикстуре — это и делает сравнение честным.

Второе число к плотному поиску отношения не имеет и требует отдельного разбора: стемминг спеки 010 заводился ради морфологии, а по замеру она проходит в одном случае из шести.

## Гейты T012 и T017 неисполнимы в текущем виде

Найдено 16.09.2026 при подготовке замера. `au eval` читает **замороженную** фикстуру, сверяя её sha256, и считает провалившимся прогон, которому понадобилась запись (`specs/010-waking-memory/contracts/cli.md` §2).

Три обстоятельства вместе закрывают дорогу:

- фикстура снята 08.09.2026 на **схеме 14**, таблицы `node_embeddings` в ней нет;
- открывается только на чтение — посчитать векторы на месте нельзя;
- пересоздать нельзя: 65 кейсов ссылаются на UUID того снимка, а 16.09 из живой базы удалено 5137 узлов, и часть этих UUID больше не существует.

Что при этом **возможно** и от векторов не зависит: точка отсчёта выше и кросс-язычные кейсы — англоязычных заметок в фикстуре 7054, материала достаточно.

Направление решения (не решение): файл-спутник предпосчитанных векторов рядом с фикстурой, со своим sha256, прикладываемый к её копии на время прогона. Фикстура остаётся неизменной, кейсы продолжают работать, 17828 векторов считаются один раз, а не на каждый прогон оценки.

## Архитектура
Пайплайн: `Query → [FTS5 BM25 top-50] + [dense KNN top-50] → RRF (k=60) → top-12 seeds → Graph 2-hop → ~20-30 candidates → Reranker → top-5`.
