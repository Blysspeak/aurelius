# Implementation Plan: Гибридный поиск и Dense Retrieval

**Branch**: `011-dense-retrieval` | **Date**: 2026-09-13 | **Spec**: [spec.md](./spec.md)

## Technical Context

**Language/Version**: Rust 2021 (workspace: `aurelius-core`, `au`, `aurelius`, `aurelius-sync-server`).
**Primary Dependencies**: `rusqlite`, `fastembed` (runtime для BGE-M3 и Qwen3-Reranker).
**Storage**: SQLite, WAL. `nodes_fts` и `nodes_stem_fts` остаются. Новая таблица `node_embeddings` через `sqlite-vec` (миграция v15→v16, уже в коде). Новая таблица `embedding_queue` для фазы D (миграция v16→v17, см. `data-model.md`).

## Фазы реализации

| Фаза | Что делает | Где |
|---|---|---|
| A | sqlite-vec + схема (DDL only). Миграция v15→v16: таблица `node_embeddings` (vec0, int8, 1024d). Статическая линковка sqlite-vec в rusqlite bundled. | `db.rs`, `Cargo.toml` |
| B | fastembed + офлайн-индексация. Новый модуль `embed.rs`. `fastembed` в Cargo.toml. Команда `au db reindex-embeddings`. Contextual prepending. | `embed.rs`, `commands.rs`, `Cargo.toml` |
| C | dense retrieval + RRF. KNN-поиск через sqlite-vec в `search.rs`. RRF-слияние FTS5 + dense scores (k=60). `r` = нормализованный RRF-скор. Вектор самого поискового запроса не считается локально: `au recall` и MCP-поиск — тонкие клиенты, шлют текст запроса демону по сокету `$AURELIUS_HOME/embed.sock` и получают обратно вектор 1024d (T023, протокол — `data-model.md` §6); KNN по `node_embeddings` клиент выполняет сам. Демон недоступен → откат на FTS5-only с явной пометкой в выводе (см. «Важные ограничения» ниже). | `search.rs`, `traverse.rs` |
| D | embedding через очередь и демон. `memory_add` / `add_node_full` кладёт id узла в таблицу `embedding_queue` (миграция v16→v17) и возвращается немедленно — модель при записи не грузится. `au daemon` (уже существующий долгоживущий процесс, владеющий часами напоминаний) держит BGE-M3 в памяти постоянно и на каждом такте разбирает очередь пачками, включая Contextual Prepending. Отвергнуто: синхронный расчёт из исходной редакции плана (~15мс) — верен только для процесса, держащего модель в памяти постоянно, а `au` короткоживущий: на каждый `au note` пришлось бы грузить 2.2 ГБ весов заново, это секунды, а не 15 мс; кроме того, это противоречит задаче трекера `f7649880` (незаблокированная запись <10 мс, фоновая досчётка пачками). Риск: свежая заметка видна векторному поиску не мгновенно, а к ближайшему такту демона — гейт T014 сформулирован через такт демона, а не через «сразу». | `graph/crud.rs`, `db.rs` (миграция `embedding_queue`), `commands.rs` (`daemon_tick`), `embed.rs` |
| E | reranker (опционально) + выбор устройства. `fastembed::TextRerank` с Qwen3-Reranker-0.6B. Top-30 после графа → reranker → top-5. Демон при старте пробует GPU, при неудаче откатывается на CPU; решение принимается один раз за запуск и пишет в журнал, какой путь выбран (риск: BGE-M3 ~1.2 ГБ VRAM + реранкер ~1.3 ГБ = 2.5 ГБ на карте 8 ГБ, которую делят другие модели). | `traverse.rs`, `embed.rs` |

## Важные ограничения
1. Существующий FTS5 не ломать.
2. Q4 квантование для инференса запрещено.
3. Формат `au snapshot --json` не трогать.
4. Путь к весам моделей — только через переменную окружения `AURELIUS_MODELS_DIR` (по умолчанию `$AURELIUS_HOME/models`), не хардкод. Заменяет `PathBuf::from("/home/blyss/.local/share/aurelius/models/")` в `crates/aurelius-core/src/embed.rs:7`. Отсутствие весов по пути — внятный отказ с указанием ожидаемого пути, не паника.
5. Векторизация поискового запроса на чтении обязана идти через демон (решение владельца 16.09.2026, «пусть демон несёт») — CLI и MCP-серверу грузить веса самим запрещено, иначе на карте 8 ГБ вместе с реранкером не помещаются три и более копии модели (см. `spec.md`, Clarifications). Если демон недоступен — поиск ОБЯЗАН откатиться на полнотекстовую FTS5-выдачу с явной пометкой отката в выводе, а не упасть и не выдать гибридный результат молча деградировавшим до FTS5: тихая деградация неотличима снаружи от намеренно более глупого поиска.
